## §2 已定决策（不得推翻，不得重新论证）

| 决策 | 结论 | 依据 |
|---|---|---|
| 框架 | **留在 WinUI 3**，不迁 Uno/Avalonia | 需要原生 Win11 效果（Mica/Fluent）；Uno 的 Windows head 底层同为 WinUI3，迁移无收益；Avalonia 是高仿非原生 |
| 主题方案 | **三规则**（§4 Phase 1）根治，不引入第三方主题库 | 根因明确可规则化（§3.1） |
| 状态联动 | **CommunityToolkit.Mvvm 的 `WeakReferenceMessenger`** | 已是项目依赖，框架无关，零新增成本 |
| DI | 保持 `Microsoft.Extensions.DependencyInjection`，规范为**构造函数注入** | .NET 标配，仅清理用法 |
| 多平台 | 不迁移，但**保持 UI 层薄**（VM/DI/数据层可复用）以保留将来可能性 | 架构原则 |

## §3 根因档案（执行 AI 必须先理解，防止重新踩坑）

### 3.1 主题冻结机制（本项目最重要的一条）
WinUI 3 中 `Application.Current.RequestedTheme` **在第一个窗口创建后即冻结，运行期设置会抛异常**。运行期深浅色切换实际依赖**窗口根元素的 `RequestedTheme`**（子元素继承）。因此：

> **凡是运行期通过 `Application.Current.Resources[key]` 解析主题画笔的代码，拿到的是"启动时冻结的主题"的画笔——窗口切浅色时拿到深色画笔（近白色），造成白字白底。**

本项目已实证：日志记录 `root.RequestedTheme=Light appTheme=Dark`，代码解析 `TextFillColorSecondaryBrush` 得到 `(255,255,255,197)`。

**已建好的基础设施：**
- `Helpers/ThemeBrush.cs`：`ThemeBrush.For(element.ActualTheme, key)` / `Resolve(dark, key)` —— 按元素实际主题从 ThemeDictionaries 解析；
- `Themes/StarMarkTheme.xaml`：显式双主题调色板 `AppAccentBrush / AppAccentSoftBrush / AppMutedBrush / AppSuccessBrush / AppCautionBrush`（Light + Default 两套）；
- `Helpers/ThemeManager.IsAppDark()`：读主窗口根元素 ActualTheme（已修正，勿改回读 Application）。

### 3.2 本项目历史踩坑清单（反模式，改造中禁止引入）
| # | 反模式 | 正确做法 |
|---|---|---|
| 1 | XAML 动态绑定不写 `Mode=OneWay` | `x:Bind` 默认 **OneTime**，动态属性必须显式 `Mode=OneWay` |
| 2 | ItemsRepeater 模板内用 `{Binding}` | ItemsRepeater **不设置 DataContext**，`{Binding}` 静默失效；必须 `x:Bind`（本项目曾因此导致标签点击全部无效） |
| 3 | 代码里 `Application.Current.Resources[key]` 取画笔 | `ThemeBrush.For(element.ActualTheme, key)` 或 XAML `{ThemeResource}` |
| 4 | 重写 `Window.OnClosed` / 使用 `Window.Closing` | WinUI 3 Window 无 OnClosed 可重写（用 `Closed` 事件）；WinAppSDK 2.4 无 `Window.Closing`（用 `AppWindow.Closing`） |
| 5 | `AppWindow.Move(int,int)` | 签名是 `Move(PointInt32)` |
| 6 | 仓储 SELECT 列序与 `MapItem` 索引不对应 | 改 SELECT 列表必须同步改 `ItemRepository.MapItem` 的列序注释与索引（曾因此 pinned 列错位读成 notes） |
| 7 | 无保护的 `async void` 事件处理器 | 必须 try/catch + `StarLog.Error` 带上下文（id/uri） |
| 8 | 构建不带 `-p:Platform=x64` | 默认 AnyCPU 会触发 WinAppSDK 架构错误 |
| 9 | 同步 upsert 覆盖用户状态 | `hidden/pinned/notes` 是用户状态，Upsert 时必须保留（已有回归测试，勿破坏） |
| 10 | 静默吞异常 `catch {}` | 至少 `StarLog.Error`；用户可见操作失败要有 InfoBar/提示 |
| 11 | 每次事件新建 `DispatcherTimer` | 单实例复用（Stop/Start） |
| 12 | 沙盒/权限问题写死路径 | 遵循 `STARMARK_*` 环境变量覆盖约定（见 `SettingsStore.ResolveSettingsPath`） |

### 3.3 日志与诊断
- 日志门面 `StarLog`（`%LOCALAPPDATA%\StarMark\logs\starmark-YYYYMMDD.log`），关键路径必须打点。
- 开发诊断钩子：环境变量 `STARMARK_START_PAGE` / `STARMARK_START_QUERY` / `STARMARK_DIAG` / `STARMARK_SIM_QUERY`（见 MainWindow 构造函数），可用作自动化冒烟。

**验收：** 0 错误 0 警告；测试全绿；git commit「chore: phase0 stabilize」。

### Phase 1 · 主题系统根治（三规则落地）
**目标：** 让"主题切换出 bug"这类问题在结构上不可能再发生。
1. **清零违规点**：`grep -rn "Application.Current.Resources" src/StarMark.UI --include="*.cs"`，逐处改为：
   - 画笔 → `ThemeBrush.For(this.ActualTheme, "AppXxxBrush")`（组件窗口用各自根元素 ActualTheme）；
   - 样式（如 SecondaryButton）→ `Application.Current.Resources` 取 **Style** 不受主题影响，可保留，但需注释说明"仅 Style 查找，非画笔"；
2. **补齐调色板缺口**：清理过程中若发现现有 `App*Brush` 键不够用（如需要 CardBackground/Divider 的代码侧引用），在 `StarMarkTheme.xaml` 的 ThemeDictionaries 补齐 Light/Default 两套，色值对照 WinUI 设计资源（Light 下 `#5C000000` 透明度写法）；
3. **组件窗口主题重建**：`WidgetWindow`（及所有独立窗口）订阅根元素 `ActualThemeChanged`，重建代码构建的 UI（各 *Widget 若全 XAML + ThemeResource 则无需处理，只有代码构建控件的地方需要重建）；窗口根元素启动时应用主窗口当前 `RequestedTheme`（保持全窗口一致）；
4. **守门测试**：新增单测或 SmokeTest 断言"src/StarMark.UI 下 .cs 文件中 `Application.Current.Resources` 后跟 Brush 强转的匹配数为 0"（写一个 grep 型测试用例，读源文件断言，防止回归）。
**验收：** §6 质量门 + 浅色/深色各截屏核对（主窗、设置页、任一组件窗、ContentDialog）；git commit「fix: theme rules enforced」。

### Phase 2 · 多窗口状态联动（Messenger）
**目标：** 主窗 ↔ 组件窗 ↔ 托盘的状态变化实时联动，不靠重查数据库。
1. 在 `StarMark.UI` 定义消息类型（建议 `Messaging/Messages.cs`）：
   - `record ItemsChangedMessage(IReadOnlyList<long> ChangedIds)` —— 条目增删改（置顶/隐藏/标签/笔记后发送）；
   - `record WidgetsVisibilityChangedMessage(IReadOnlyList<WidgetKind> Visible)` —— 组件开关变化；
   - `record ThemeChangedMessage(ElementTheme Theme)` —— 主题切换（各窗口根元素跟随）；
2. **发送方**：`ItemCardActions`（TogglePin/ToggleHidden/EditNote/EditTags 成功后）、`WidgetManager`（Show/Hide/SetEnabled 后）、`MainWindow.ThemeButton_Click` 与设置页主题应用处；
3. **接收方**：各组件窗口中依赖条目数据的（QuickLaunch 的置顶列表、ItemGrid 等）收到 `ItemsChangedMessage` 后增量刷新；`ThemeChangedMessage` 由所有独立窗口订阅并应用到根元素；
4. **注意**：Messenger 回调在发送方线程执行——UI 更新必须 `DispatcherQueue.TryEnqueue`；使用 `WeakReferenceMessenger.Default` 且窗口 `Closed` 时 `Unregister` 防泄漏。
**验收：** 手动场景——①主窗卡片置顶 → QuickLaunch 组件列表无需手动刷新即更新；②切换主题 → 所有已开组件窗同步换肤；③测试全绿；git commit「feat: messenger state sync」。

### Phase 3 · DI 规范化
**目标：** 消除 ServiceLocator 兜底，依赖编译期可见。
1. `grep -rn "App.Services.GetService" src/StarMark.UI --include="*.cs"` 逐处评估：
   - 页面 ViewModel 获取 → 改构造函数注入（页面由 Frame 导航创建，可在页面构造里保持从容器取，但去掉 `?? new XxxViewModel(...)` 兜底，取不到直接抛——问题应显性化）；
   - 静态帮助类（ItemCardActions）里的 GetRepo → 保留但集中到一个 `App.Services` 扩展方法（`GetRequiredItemRepository()`），禁止散落模式匹配；
2. 统一 ViewModel 生命周期标注（单例 VM 的保留理由注释：跨页保留状态；瞬态 VM 同理）；
3. **禁止**引入第三方 DI 框架。
**验收：** 无 `?? new XxxViewModel` 模式残留；功能回归（各页面正常导航与刷新）；git commit「refactor: di cleanup」。

### Phase 4 · 桌面组件完善与置顶链路修复

## §5 硬性约束（违反即返工）

1. **不更换框架/不引入 Uno/Avalonia/第三方主题库/第三方 DI**（§2 决策表）；
2. **不改动** `D:\Visual Studio Code\Something\StarMark`（浏览器扩展项目）与 `DeskBox-ref`（参考仓库，只读）；

4. **不引入新 NuGet 依赖**（Messenger/DI 均已就位）；确有必要时先停下来说明理由征得同意；
5. **禁止 `catch {}` 静默吞异常**（§3.2-10）；禁止无保护 `async void`；
6. 每个改动的代码注释只解释"约束/原因"，不写"我改了什么"；
7. Windows 专属 API（AppWindow/托盘/P/Invoke）只允许出现在 UI/Integrations 层，Core/Data/Abstractions 保持平台无关（多平台保留原则）。
