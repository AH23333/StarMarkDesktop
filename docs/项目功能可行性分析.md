# 项目功能可行性分析

**项目代号：StarMark（桌面端）**


## 一、项目概述

### 1.1 产品定位

一款Windows桌面应用，将本地文件、浏览器书签、GitHub Stars整合为统一的“可操作条目”，提供跨源搜索、统一标签、规则引擎和系统级集成。

### 1.2 核心亮点

**亮点一：统一条目模型。** 本地文件、浏览器书签、GitHub Star在数据库中是同一张 `items` 表的记录，通过 `type` 和 `source` 字段区分。标签、笔记、搜索索引、规则引擎全部跨源统一操作。用户搜索时结果混排展示，不需要在三个不同工具之间切换。

**亮点二：系统级深度集成。** Shell扩展嵌入资源管理器右键菜单，全局快捷键在任何界面下唤出统一搜索框，系统托盘常驻后台运行。这些能力是浏览器插件和Web应用完全无法实现的。

**亮点三：Everything极致搜索复用。** 通过Everything SDK复用已构建的内存索引，文件搜索延迟在毫秒级别，零索引维护成本。Everything v1.5的命名管道（Named Pipes）IPC比旧版WM_COPYDATA方式快约5倍，保持管道连接打开时几乎无IPC延迟。

**亮点四：跨源规则引擎。** 规则条件可以跨类型组合——文件规则（扩展名、大小、修改时间）和URL规则（Star数、语言、Topic、书签域名）使用同一套语法。“如果Star数>500且Topic包含rag，自动打标签”和“如果下载文件夹有新的PDF文件，自动移动到论文文件夹”可以共存于同一个规则引擎。


## 二、技术栈选型

### 2.1 推荐技术栈

| 层级 | 选型 | 理由 |
|------|------|------|
| UI框架 | WinUI 3 | 原生Fluent Design，与Windows 11风格一致 |
| MVVM | CommunityToolkit.Mvvm | 源生成器减少样板代码 |
| 本地文件索引 | Everything SDK（命名管道模式） | 毫秒级搜索，零索引维护 |
| 数据存储 | SQLite（Microsoft.Data.Sqlite） | 统一存储条目、标签、笔记、规则 |
| 全文搜索 | SQLite FTS5 + 外部表JOIN | 文本索引与数值列分离 |
| 全局快捷键 | P/Invoke RegisterHotKey | 成熟方案 |
| Shell集成 | SharpShell（可选组件，进程外COM服务器） | 上下文菜单、预览处理器 |

### 2.2 WinUI 3的客观约束

微软在2026年5月宣称实现了WinUI 3的“leap forward”级别性能优化，文件管理器启动路径中内存分配减少41%、函数调用减少45%、WinUI代码执行时间降低25%。但必须正视以下约束：

**性能优化尚未默认启用。** 微软承认这些优化伴随默认控件样式的破坏性改动，某些高度自定义旧应用可能受影响，高性能路径暂时为“选择加入”，计划在WinAppSDK 3.0/4.0以上版本才逐步转向默认启用。

**开发工具缺失是确定的约束。** Visual Studio的XAML设计器目前不支持WinUI 3项目，所有布局必须手写XAML。对于格子化编排界面和规则配置面板这两个核心UI模块，开发效率会显著低于WPF。

**这些约束不影响可行性，但影响开发进度和初期用户体验的上限。** 建议接受当前状态，同时关注WinAppSDK 3.0的发布节奏。


## 三、集成级别分级

### 3.1 第一级：立即集成（低风险、高价值）

| 项目 | 集成方式 | 核心价值 | 关键技术约束 |
|------|---------|---------|-------------|
| **Everything SDK** | NuGet包（EverythingNet）深度集成 | 毫秒级文件搜索，零索引维护 | SDK非线程安全，一次只能处理一个查询；需检测主程序运行状态 |
| **Ditto 剪贴板数据库** | 只读读取SQLite数据库（`Ditto.db`） | 剪贴板历史纳入统一条目模型 | 数据库路径为 `%APPDATA%\Ditto\Ditto.db`，含时间戳、内容长度、数据类型等字段 |
| **TagSpaces 标签模型** | 功能借鉴（标签随文件走的哲学） | 标签不锁定在专有数据库中，可导出为sidecar文件 | TagSpaces将标签存储在文件名或`.ts`隐藏文件夹中的JSON sidecar文件里；建议采用SQLite集中管理同时提供导出选项 |
| **QuickLook 预览架构** | 功能借鉴（`IViewer`接口设计） | 搜索结果中空格键触发内嵌预览 | `IViewer`接口定义五个核心方法：`Init`、`CanHandle`、`Prepare`、`View`、`Cleanup` |
| **Flow Launcher 插件架构** | 功能借鉴（`IPlugin`/`IAsyncPlugin`接口） | 插件化搜索扩展机制 | `IAsyncPlugin`提供 `CancellationToken`，允许插件检测用户是否输入了新查询 |

**关于Everything SDK许可：** 项目仅个人开源，不商用。Everything主程序核心采用MIT许可证，SDK可自由使用、分发和修改。分发时在关于页面标注版权归属即可。

**关于Everything线程安全约束的缓解：** SDK一次只能处理一个查询。需要在应用层实现查询队列和取消机制——当用户输入新关键词时，取消前一个查询并释放SDK资源，再发起新查询。

**关于Everything查询标志优化的缓解：** 需要根据当前搜索结果面板实际展示的字段，动态选取最小必要的查询标志集。例如，如果列表不展示文件大小，就不请求 `EVERYTHING_REQUEST_SIZE` 标志。


### 3.2 第二级：中期规划（需要架构设计）

| 项目 | 集成方式 | 核心价值 | 关键技术约束 |
|------|---------|---------|-------------|
| **Lertaro 索引方案** | 功能借鉴（NTFS USN Journal + $MFT解析） | 自建索引替代Everything依赖 | 开发成本高，需要深入理解NTFS底层结构 |
| **DeskBox 格子化界面** | 功能借鉴（“只引用不移动文件”设计） | 高度可定制的格子布局 | 基于WinUI 3 + Windows App SDK，技术栈一致 |
| **Asset Manager 插件系统** | 功能借鉴（进程外声明式插件架构） | 插件运行在独立Worker中，通过JSONL协议通信 | 架构复杂度中等，适合作为远期插件系统参考 |
| **Knowledge Base 双向链接** | 功能借鉴（FTS5 + 知识图谱） | 笔记模块的双向链接与知识图谱 | 基于Tauri 2.x + Rust，与WinUI 3栈不同，建议只借鉴数据模型 |
| **Windows-MCP 自动化预留** | 独立组件（C#编写的MCP服务器） | 为未来自动化工作流预留标准化接口 | 需要.NET 9 SDK，MVP阶段不纳入 |

**关于SQLite FTS5的数值查询性能陷阱：**

你的搜索场景会频繁使用数值条件——按Star数筛选（`stars_count > 500`）、按修改时间筛选（`updated_at > 本周`）、按文件大小筛选（`file_size > 100MB`）。FTS5的倒排索引只加速文本匹配，当查询中包含非文本条件时，SQLite会做全表扫描，性能可能下降超过千倍。

**解决方案：将数值列放在外部普通表中，查询时先通过FTS5找到rowid列表，再JOIN到外部表做数值过滤：**

```sql
-- 正确做法：FTS5先缩小文本范围，JOIN外部表做数值过滤
SELECT i.* FROM items i
JOIN items_fts f ON i.rowid = f.rowid
WHERE f.items_fts MATCH 'rag' AND i.created_at > 1700000000;
```

Navicrome项目通过类似的“两阶段查询”策略——轻量阶段获取分页rowid，hydration阶段再JOIN完整数据——避免了对大结果集的昂贵JOIN操作。这个架构必须在数据模型设计阶段就确定，不能等到性能问题出现后再重构。


### 3.3 第三级：长期愿景（复杂度高）

| 项目 | 集成方式 | 核心价值 | 关键技术约束 |

## 六、核心结论

**技术可行性：** 核心功能（统一条目模型、Everything集成、标签系统、统一搜索）在C#生态中完全可行，技术路径清晰。第一级集成的所有项目均有成熟的实现方案和已验证的集成路径。

**主要风险集中在三个工程约束上：** WinUI 3性能优化尚未默认启用、FTS5数值查询需要外部表JOIN架构、Everything SDK的线程安全限制。这些约束不会阻止产品完成，但会影响开发进度和用户体验的上限。

**最大的不确定性不在代码层面，而在产品层面：** 用户是否愿意接受Everything依赖（尽管体积仅约2MB）、WinUI 3的视觉风格是否值得无设计器的开发代价、以及跨源统一管理的价值是否足以驱动用户从现有工具迁移。

**建议的开发起点：** Phase 1的SQLite数据模型 + Everything SDK集成 + 统一搜索。这三个模块是产品的技术地基，也是最核心的差异化亮点。先跑通这个闭环，再逐步叠加其他集成能力。
