## P-1（AC-1 安全审计遗留）：`file://` 远程主机 / UNC 的进一步收敛
- **背景**：AC-1 已在 `LauncherEx.OpenAsync` 前置协议白名单闸门（`LaunchGuard.IsAllowedScheme`，仅放行 http/https/file），挡住了 `javascript:` / `data:` / `ms-msdt:` / 自定义协议等借 Shell 协议处理器执行的污染记录。但 `file` scheme 本身仍放行任意主机：`file://attacker/share/payload` 形态的 URI 会走 `StorageFile/Folder.GetFromPathAsync`，若路径不可达则退化到 `Launcher.LaunchUriAsync` → 可能触发对远程主机的 SMB 访问，存在 NTLM 哈希泄漏面。
- **为何未在本批次落地**：`file://` 有两斜杠（Everything 侧 `file://C:/...`，主机位被历史歧义处理）与三斜杠（标准 `file:///C:/...`）两种形态，用 `Uri.Host`/`LocalPath` 区分「本地盘符」与「真实远程主机」在 .NET 上有已知歧义（见 R-P1-8 与 `LocalFileIdentity.TryPathFromUri` 往返契约）。错误收敛会打挂正常本地文件打开，须真机回归全部 file 条目来源。
- **选项**：(A) 判定 `Uri.Host` 非空且非 localhost/空 → 视为远程直接拒；(B) 仅放行 `LocalPath` 能还原成有效本地盘符/UNC 白名单的；(C) 维持现状（scheme 白名单已挡住高危 RCE 面，UNC 泄漏面留待真机批次）。
- **我的默认处置**：本自主会话取 (C)，不改动可正常工作的本地打开路径；把 (A)/(B) 留给你在有真机回归时定夺。

## P-4（AE 评审附带发现）：`UriNormalizer.Normalize` 不归一 query 参数顺序
- **背景**：AE 批自审 `StarMark.Abstractions.UriNormalizer` 时发现：`StripTrackingParams` 按**原顺序**保留参数，未排序。故同一资源的 `?a=1&b=2` 与 `?b=2&a=1` 归一后仍是两个不同串 → 两个 `source_id` → 标签/笔记被**分裂到两条记录**。这与该文件自述目的（「同一资源的不同 URL 变体归一为同一 source_id，避免重复条目把标签/笔记分裂」）直接冲突；现有 `UriNormalizerTests`（幂等/默认端口/IPv6）也未对参数顺序作断言，即当前无测试锁定"保序"这一行为。
- **为何未在本批次落地**：修法是 query 参数按 key 排序重建——但这是**去重语义变更**，blast radius 不小：① 已入库行的旧 `source_id` 不会自动改，排序只对"新写入/再同步"生效，可能让老键与新键并存反而短暂裂成两条（需配一次全库 source_id 重算迁移才干净）；② 极少数站点确实 query 参数顺序敏感（签名/回调），排序会错误合并。属"改去重口径"的产品级决策，非纯可机检缺陷，不擅改。
- **选项**：(A) query 参数按 key（+值）稳定排序 + 配一次重算 source_id 的迁移；(B) 维持现状（承认顺序变体会裂，多数书签参数顺序稳定，代价低）；(C) 仅对已知可重排的参数集排序，白名单外保持原序。
- **我的默认处置**：本会话取 (B) 维持现状、不改可正常工作的去重键；把 (A)/(C) 连同"是否要做全库 source_id 重算迁移"交你定夺。若选 (A)，我会先补一条 `Normalize_SortsQueryParamOrder` 回归再动实现。
- **影响面**：书签/来源去重粒度；若落地需伴随迁移，风险中等故未擅动。

## P-5（AJ 后台代理附带发现）：同步只增改不删——上游已移除的条目永久残留
- **背景**：`IItemSource.FetchAsync` 契约明确是「拉取**全量**条目」（IItemSource.cs:22），`SyncCoordinator.SyncAllAsync` 对每个源仅 `UpsertAsync`（存在则更新、不存在则插入），**从不删除**本次全量结果里缺席的旧行。后果：
  - GitHub 取消 Star、浏览器书签被删、Ditto 记录被过期清理/手动删——这些条目在上游已消失，但 StarMark 的 `items` 表里**永远留着**，且在「全部/搜索」里仍可被搜到、可打开（甚至可能指向已失效资源）。
  - 已核实：全仓无任何 `DELETE FROM items` 的同步对账路径（`DataChangeHub.Prune` 只是弱引用订阅者清理，无关条目）。`sync_state` 记 `last_synced_at`/`schema_version`，但无「本源上次全量键集」快照，故当前也无从判断哪些行是"这次没再出现"。
- **为何未在本批次落地**：这是**产品语义决策**而非纯可机检缺陷——"同步是否应对账删除"取决于你想要的是「只增归档（保留历史，宁滥勿缺）」还是「严格镜像上游（源删即删）」。两种都合理，删错会丢用户可能仍想留的条目/其标签笔记，blast radius 中等，不擅改。
- **选项**：(A) 严格镜像：每源同步时按 `(source, source_id)` 对账，本次全量未出现的行删除（需先给 `sync_state` 存"上次键集快照"或在删除前比对 `last_synced_at < 本次开始` 的旧行；对**非全量/分页截断**的源如 Ditto `MaxSync=500` 要防误删头部之外的旧记录）；(B) 软删/标记失效：不删行，打 `stale` 位在 UI 灰显，用户可一键清理；(C) 维持现状（只增归档），仅在设置页给「清理失联条目」手动按钮。
- **我的默认处置**：本会话取 (C) 维持现状（当前行为对用户无破坏，最多多显示）；把对账删除口径交你定。**关键坑位提醒**：若选 (A)，必须区分「源确实返回全量」与「源被 `MaxResults`/`MaxSync` 截断」——截断源做全量对账会把未出现在首页的合法历史条目误删。Ditto(`MaxSync=500`)、Everything(分页)、以及任何 `FetchAsync` 内部带 LIMIT 的源都不满足"全量"前提，除非其 `FetchAsync` 改为无上限游标遍历。
- **影响面**：条目生命周期与数据保留策略；若落地需按源逐个确认"是否真全量"，涉及 UI 删除反馈与误删护栏，风险中等故未擅动。

## P-6（AK GitHub 复核）：「最近 Star」排序实为按仓库 push 时间，非用户 star 时间
- **背景（`[读码定位]`）：** 批次 Y 落地的搜索结果排序里 `sort=starred`（"最近 Star"）在 `ItemRepository.cs:71` 取 `json_extract(extra_json,'$.StarredAt') DESC`；而 `GitHubSource.MapToItem:93` 把 `StarredAt = ParseUnixTime(repo.PushedAt)` —— 即**仓库最后一次 git push 的时间**，不是"用户点 Star 的时间"。两者语义差异大：一个老仓库被新近 Star 会排到很后面；一个热门仓库每天 push 会一直霸榜。
- **根因不是编码笔误，而是一个**事实上过时/错误的近似假设**：** `GitHubClient.cs:52,86-87` 注释称「starred_at 不可用，需要从 pushed_at 替代」，并把 `Accept` 设成 `application/vnd.github+json`。GitHub 文档明确：`/user/starred` 只要把 `Accept` 换成 `application/vnd.github.star+json`，响应即变为 `[{"starred_at":"...","repo":{...}}]` 信封，**starred_at 是可用的**，并非"不可用"。故这是"可实现但当年选了近似"的欠账，不是无解限制。
- **可行性（为何本自主会话未落地）：** 修法=首页 `Accept` 改 `…star+json` + 反序列化改为信封模型（`List<StarEnvelope>{ string StarredAt; GitHubStarApiModel Repo }`）+ `MapToItem` 用真 `starred_at` 填 `StarredAt`（`updatedAt` 仍可用 repo.UpdatedAt）。改动纯逻辑层面小，但**触碰 HTTP 请求头与响应结构**——本沙箱无 GitHub Token/网络，无法验证真实响应形态（W0/standing：GitHub 集成不可沙箱验、无运行证据不动可用网络码）。副作用可控：换 media type 会使 GitHub 返回不同 ETag，改后首轮同步条件请求自然落空→全量重拉一次，无害。
- **选项**：(A) 按上面修法取真 starred_at（最正确，需一次带 Token 的真机验证）；(B) 维持现状但把 UI 文案/tooltip 从"最近 Star"改"仓库最近活动"以消除误导（零网络风险）；(C) 维持现状不改（承认近似）。
- **我的默认处置**：本会话取现状不动网络代码；若你认可 (A)，我会在能真机回归 GitHub 时一并实施并补 `MapToItem` starred_at 单测（信封解析可机检，网络拉取仍需 `[v]`）。**若只是想尽快止损误导，(B) 是纯文案、我可立即落。**
- **影响面**：仅 GitHub Star 源的"最近 Star"排序语义与 `StarredAt` 展示值；不影响书签/本地/剪贴板源与其余排序档。

## P-7（AM 后台代理附带发现 F2）：本地条目「删除→撤销」丢失 item_tags（及潜在 pinned）

## P-8（AN 后台代理附带发现①）：语言筛选「下拉值 vs SQL vs 内存兜底」三处口径不一致
- **背景（`[已核实]`）：** 语言筛选存在三套互不一致的比较口径。① `SearchService.SearchAsync`(`:92-96`) 的内存兜底用 `GetLanguage(item)`(`:146`)，后者对 `item.Type != GitHubStar` **直接返回 null** → 一旦设了 `filter.Language`，所有 `file/bookmark/todo/note` 行被内存丢弃（无论 SQL 是否已命中）。② 但两处 SQL(`ItemRepository.cs:95` 搜索、`:441` 浏览) 的语言过滤是**跨全部类型**的 `json_extract($.Language)=@lang`。③ 下拉数据源 `GetStarLanguagesAsync`(`:405-429`) 只枚举 `type='githubstar'`，且返回 `LanguageCatalog.Normalize(trim(raw))` 归一值，而 SQL 拿它去和**未归一、大小写敏感**的 `json_extract($.Language)` 原样相等比较。
- **判定（为何主结论非缺陷、次结论转决策）：** 代理"内存兜底静默删掉所有非 star 命中"的**头条结论实为按设计**——`LanguageDetector` 类注释(`:8-9`) 明写"语言下拉的语义是『按条目的编程语言筛选 star』"，`GetStarLanguagesAsync` 也只列 star 语言。故"选 Rust 只回 star"符合既定产品语义，非 bug。**真正待决的是次级不对称**：(a) 若将来希望语言筛选**跨类型**（书签直链 `.rs`、Everything 命中的源码文件），则 `GetLanguage` 的类型门禁是拦路缺陷；(b) 即便维持 star-only，**下拉归一值 vs SQL 原样大小写敏感比较**是隐患——`EnsureLanguage`(`:52`) 对"已带 PascalCase `Language` 键"的 extra_json **原样返回、不归一**，故若 GitHub API/种子曾回传非规范大小写语言名（如 `"c++"`），下拉给出归一的 `"C++"`，SQL `"c++"="C++"`（BINARY 排序）落空 → 该选项点开 0 结果。此触发需"库里存了非规范大小写的 Language"，本沙箱无该样本、无运行证据。
- **选项**：(A) 维持 star-only，但把 SQL 侧语言比较也改为**归一 + 大小写无关 + trim**（`trim(... ) COLLATE NOCASE = trim(@lang) COLLATE NOCASE`），与下拉和内存兜底(`OrdinalIgnoreCase`)三处对齐；纯可机检、低风险，但要动两处 SQL。(B) 让语言筛选跨类型生效（`GetLanguage` 去类型门禁、改读任意类型 `$.Language`），并让 `GetStarLanguagesAsync` 覆盖非 star——**属产品语义扩张**，需你确认是否要"文件/书签也按语言筛"。(C) 维持现状。
- **我的默认处置**：本会话不改（头条为按设计、次条触发未证实），倾向若你认可则取 (A) 做口径对齐（最小且可机检），(B) 需明确产品意愿再做。
- **影响面**：主界面语言下拉 + 文件夹树语言过滤的实际命中。

## P-10（AQ 后台代理附带发现②）：`WidgetStorage.Normalize` 在 **Load 读路径**做 `Take(200/100)` 限量 → 读取即毁数据

- **可机检定位**：`WidgetStorage.Normalize`（`src/StarMark.Core/Widgets/WidgetStorage.cs:481-496`）对每实例的 Todos/Notes/Links 施加 `.Take(200)/Take(100)/Take(100)`，而 `Normalize` 同时被 **`Load()`**（`:343/349/358/367`）与 `Save()`（`:391`）调用——限量因此发生在**读路径**上：`Load()` 返回的内存模型已被裁到上限，随后任何 `Load()→改→Save()` 都会把超出部分当作不存在、永久写回缺失。

- **佐证"读路径限量"非有意设计**：展示层自带 `QuickNoteWidgetViewModel.DisplayLimit = 30`；`Take(200)/Take(100)` 全仓仅此一处、无 UI 强制、无任何用户可见文案提及。读路径裁剪既无展示收益、又执行破坏性删除，且 widgets.json **不在 DB 备份内**、常规 Save 不落 `.bak`、无日志行，故丢失**不可恢复**（仅 OneDrive / 文件历史可救）。

- **影响面**：仅"单实例内容条数超过对应 `Take` 上限"者；未超限的常规用户不受影响，但一旦超限即为静默、不可恢复的丢失。

## P-13（AT 安全深挖附带发现）：`StarLog` 未剥离消息内 CR/LF → 日志伪造（log forging）
- **可机检定位**：`StarLog.Write`（`src/StarMark.Abstractions/StarLog.cs:28-41`）把 `message` **原样**拼进 `[{时间}] {LEVEL} {message}{NewLine}` 后 `File.AppendAllText`，全程不对消息内的 `\r`/`\n` 作剥离或转义。任何**受外部影响的串**（备份文件名、被篡改备份里的字段、来源标题、`Error(msg, ex)` 里异常 ToString 携带的用户数据）一旦含换行，即可在日志里另起一行、伪造出**没有 `[时间戳] LEVEL` 前缀的任意后续行**，破坏「一行一事件」不变式；下游日志解析/审计/grep 会被喂入伪造条目或漏检真条目。
- **为何本会话未落地（属方法论边界，非"不算缺陷"）**：① 纯修法（`Write` 拼串前 `message.Replace("\r","\\r").Replace("\n","\\n")`）虽小且可机检，但**无 `LogDirectoryOverride` 测试钩子**——`LogDirectory` 恒指向真实 `%LOCALAPPDATA%`，单测写入即污染真实用户目录，故无法像 `BackupService.SnapshotDirectoryOverride` 那样给临时目录做「注入一行含换行的消息 → 断言物理行数仍为 1」的回归测。② 不擅自改跨切面日志门面，也不擅自往门面里塞一个 `internal static` 钩子（该模式本身是需认可的约定），故按纪律转决策。
- **选项**：(A) 先加 `LogDirectoryOverride`（复刻 `BackupService.SnapshotDirectoryOverride` 现有模式）→ 再在 `Write` 里对 CR/LF 转义 → 补上述临时目录回归测；(B) 仅做 CR/LF 转义、暂不引测试钩子（改动更小但无测锁）；(C) 维持现状。
- **我的默认处置**：本会话不改；建议后续取 (A)（转义 + 钩子各一处、均低风险，且钩子与既有 SnapshotDirectoryOverride 同构）。
- **影响面**：仅日志完整性与可审计性；不影响核心功能，也不扩大 RCE 面（是"伪造既有日志"而非"执行"）。
- **AX 补充（先前未记的关键权衡：栈可读性）**：上面 (A)/(B) 的 `message.Replace("\r",…).Replace("\n",…)` 会**一并压平 `Error(msg, ex)` 的堆栈**——因 `StarLog.cs:28` 先把 `{message} {ex}` 合成一个 `message` 再交给 `Write`，`ex.ToString()` 里的合法换行（stack trace）会被转义成单行，损害崩溃排查可读性。因此"统一转义"不是零代价：它把每条日志强制变单行（对 grep/解析更友好，但人读栈变差）。三个更细的落点：
  - **(A1) 只净化 `Write` 顶层拼接、不动栈**：给 `Error(msg, ex)` 单开一条路径——`msg` 转义 CR/LF，`ex` 保持原样多行，但把栈的每个续行加固定前缀（如 `\n    ↳ `）使其不以 `[时间]` 开头，从而**既防伪记录又不牺牲栈**。可机检测：注入含 `\n[2099-01-01] ERROR 伪造` 的 msg → 物理行数仍为 1；含 `\n` 的 ex → 续行不带 `[ISO] LEVEL` 前缀。
  - **(A2) 全量单行化**：接受栈折成一行（JSON-lines 风格），实现最简、机器解析最佳，人读最差。
  - **(A0) 仅净化 msg、ex 原样**（P-13 原 (A)）：最小改动，但栈里的外部数据（如含换行的被污染 title 经 `ex.Message` 流入）仍可伪造——防得不全。
  - 结论修正：**推荐 (A1)** 取代原默认 (A)——它是唯一"闭合伪造 + 保留栈可读 + 防外溢到 ex.Message"三全且可机检的方案，代价是 `Error(msg, ex)` 需与 `Info/Warn` 分流。测试钩子仍按 (A) 加 `LogDirectoryOverride`。本会话仍不改（跨切面门面 + 有 devex 权衡 → 守"不擅改"纪律）。
- **✅ CD 批（2026-09-21）已按 (A1) 落地（commit `02a8edd`）**：承上"推荐 (A1)"，CD 实际实现——`Write(level, message, ex?)` 分流：`Info/Warn/Error(msg)` 走 `SanitizeMessage`（消息主体 CR/LF 折成字面量、无换行逐字节透传）；`Error(msg, ex)` 令 `ex` **不再折进 message**，改由 `StackTail(ex)` 输出——堆栈保留多行、每续行前缀四空格缩进（等价于文档设想的 `↳` 前缀，取更朴素的空格），使任何续行都不以 `[` 起始 → 伪造头 `\n[2099…] INFO evil` 即便在 `ex.Message` 里也只作缩进文本、不被 `^[时间戳]` 锚定误认新条目。**两处安全目标兼得、无栈压平代价**。
  - **修正此前"不可测"判断（价值留痕·防未来重踩）**：原"本会话未落地"理由①「无 `LogDirectoryOverride` 钩子即无法回归」被证伪——把净化逻辑抽成 **`internal` 纯函数**（`SanitizeMessage` / `StackTail`）+ 给 Abstractions 加 `<InternalsVisibleTo StarMark.Tests>`，即可**不写真实 `%LOCALAPPDATA%`、零文件 I/O、不 flaky** 地断言安全不变式（主行无裸 CR/LF、栈每行缩进、伪造头不可锚定）。`StarLogTests` 13 例覆盖，`dotnet test 541→554` 全绿。**教训**：跨切面门面的"可测性"障碍多可用「纯函数化 + InternalsVisibleTo」拆解，不必先造目录覆写钩子。

## P-18（AZ 后台代理线索）：Ditto `CF_TEXT` 按 UTF-8 解码（应为本机 ANSI/OEM 代码页），且 `FillData` 里 `CF_TEXT` 可覆盖已正确的 `CF_UNICODETEXT`
- **可机检定位**：`DittoDatabaseReader.FillData`（`DittoDatabaseReader.cs:157-167`）把 `CF_UNICODETEXT` 与 `CF_TEXT` 合并进同一 case，`DecodeText(ansi, …)` 对 `CF_TEXT`（`:194`）用 `Encoding.UTF8` 解码。但 Windows `CF_TEXT` 是**系统 ANSI/上层 OEM 代码页**（如 CP936/CP1252）而非 UTF-8 → 含 >0x7F 字节的旧式纯文本 clip 会被解成乱码。更硬的次生问题：两格式走**同一赋值分支**，`Data` 表返回行序不保证，若某 clip 同时存 `CF_UNICODETEXT`（正确）与 `CF_TEXT`（应被忽略的兼容格式），后到的 `CF_TEXT` 会**覆盖** `clip.Text`，把本来正确的宽字符正文换成按 UTF-8 误解的字节流。
- **为何本会话未擅自改**：① 正确解码 `CF_TEXT` 需 Windows 代码页——现代 .NET `Encoding.Default` 已是 UTF-8，须显式 `CodePagesEncodingProvider.Register` + 取 ACP/OEM CP，属**平台编码选择**且**只有真实 Ditto 库（含 CF_TEXT clip）能验**，沙箱不可机检其正确性；② "覆盖次序"修法（优先 `CF_UNICODETEXT`、`CF_TEXT` 仅在其缺席时兜底）虽可在 C# 侧定序，但需先确认 Ditto 对同一 clip 是否会同时落两种格式、以及优先级语义，属对第三方二进制格式的行为推断，不宜在无真机样本时拍。
- **选项**：(A) `FillData` 加"已见 `CF_UNICODETEXT` 则不被 `CF_TEXT` 覆盖"的定序护栏（纯可机检、堵死覆盖，但 `CF_TEXT`-only 仍按 UTF-8 误解）；(B) 在 (A) 之上，`CF_TEXT`-only 解码改走注册的 ACP/OEM 代码页（需 `System.Text.Encoding.CodePages` 依赖 + 真机验）；(C) 维持现状。
- **我的默认处置**：本会话不改；建议至少落 **(A)**（低风险、可测：构造含两种格式行的假 Ditto 库，断言 `Text` 取 `CF_UNICODETEXT`），(B) 待引入代码页依赖并真机验证后再定。
- **影响面**：仅以 `CF_TEXT` 承载、且含非 ASCII 的历史 Ditto clip（现代 Ditto 多用 `CF_UNICODETEXT`，面偏窄）；纯 ASCII 不受影响。

## P-19（AZ 后台代理线索）：`GitHubSource.FetchAsync` 在条目落库前就写下 ETag 检查点，崩溃窗口 + 304 短路会令新 Star 永久缺失
- **可机检定位**：`FetchAsync`（`GitHubSource.cs:42-66`）在 `:53-54` 把 `_client.CachedETag` 写进 `sync_state("github:etag")`，但**它本身不落库条目**——只 `return items`，实际 `UpsertAsync` 由调用方 `SyncCoordinator` 在其返回后执行。若进程在"ETag 已写"与"条目已 upsert"之间崩溃：下次同步读到新 ETag→首页带 `If-None-Match`→GitHub 返 **304**→`GetAllStarredAsync` 返回空（`GitHubClient.cs:72-73`）→`repos.Count==0`→`FetchAsync` 于 `:58` 直接返回空→调用方不写任何条目。于是**上一轮已拉到但崩溃丢失的那批 Star 再也不会被重新获取**，直到用户 starred 列表再次变动产生新 ETag。
- **为何本会话未擅自改（跨层签名改动，非单点低风险）**：根因是"检查点与载荷不在同一原子边界"。修法要么把 `SetSyncState(etag)` 从 `FetchAsync` 内部**移出**、改由协调器在 `UpsertAsync(items)` **成功之后**再提交；要么给 `IItemSource` 引入两阶段 `CommitAsync`。两者都触及 `IItemSource` 契约与 `SyncCoordinator` 编排（各源实现都得跟改），属**批量**改动且无运行证据佐证收益，不宜在自主批次里动热同步链。
- **选项**：(A) `FetchAsync` 不再自写 ETag，返回 items 由协调器 upsert 成功后统一 `SetSyncState`（最小语义正确，但要确保"空结果=304 未变"与"崩溃未落库"可区分）；(B) `IItemSource.CommitAsync` 两阶段（最干净、改动最大）；(C) 崩溃窗口概率低（需恰好在两写之间断电/杀进程）+ 用户可"强制全量重同步"自愈 → 维持现状并文档化。

## P-20（AZ 后台代理线索）：`ParseDropFiles` 的 `(int)pFiles` 存在符号翻转 + 头部偏移无下界校验

## P-22（BC 后台代理线索）：统一搜索去重用 `OrdinalIgnoreCase` 折叠 URI 键，与存储层的区分大小写不变式相左
- **可机检定位**：`SearchService` 合并 FTS 与实时源结果时用 `var seen = new HashSet<string>(StringComparer.OrdinalIgnoreCase)`（`SearchService.cs:84`），键为 `CanonicalizeUri(item.Uri)`（`:88`）。`CanonicalizeUri`（`:146-157`）只把 `file://` 折成本地路径，**http(s) 原样返回、保留路径大小写**，但集合比较器是 `OrdinalIgnoreCase` → 仅路径大小写不同的两个 http URI（`https://x/Docs` 与 `https://x/docs`）在去重时塌成一键、只留其一。而**存储层恰恰视其为两条**：`items.uri`/`source_id` 是 BINARY 排序（区分大小写），`source_id=Normalize(url)`（`UriNormalizer` 只小写 host、**保留 path 大小写**），`UNIQUE(source,source_id)` 不合并它们 → 两条都在库、都在 `GetAllAsync` 浏览可见，却只在搜索里少一条（"列表里有、搜不到"）。
- **为何本会话未擅自改（属去重语义/产品取舍，非崩溃非毁数据）**：① 单一 `HashSet` 比较器要精确化须改成"前缀键 + 分支"方案（`file://` 走不区分大小写因 Windows 路径本就不区分、http(s) 走 Ordinal 区分）——`OrdinalIgnoreCase` 对 file 分支是**对的**，不能一刀切换成 Ordinal；改法本身可机检，但 ② "同一 host 仅路径大小写不同的两个 URL 是否算两条结果"是**产品语义判断**：当前偏"合并防重"，改成区分大小写则"暴露更多条目、但可能放回历史脏重复"，两向各有 UX 后果，且无运行证据指认哪向是用户所愿。代理自述此条"可能是按设计"。③ 触发面窄（需用户库里真有仅大小写不同的同源兄弟 URL 且同命中一关键词）。综合 → 不擅自动热搜索链语义。
- **选项**：(A) 维持现状（保守、file 去重正确、http 罕见大小写兄弟被合并）；(B) 精确化：`seen` 键改带前缀且 http 分支用 Ordinal（`file` 仍忽略大小写），令搜索去重与 `UNIQUE(source,source_id)` 的 BINARY 不变式一致；(C) 若确认「搜索视图故意比浏览更激进合并」是设计意图，则加代码注释钉死该意图、维持行为。
- **我的默认处置**：本会话不改；倾向 **(B)**（把搜索去重对齐到存储层既有不变式是"消除自相矛盾"，非新增产品决策——库既然存两条、搜索就不该吞一条），但因 UX 可见，请确认后再落地。
- **影响面**：仅"同 host 仅路径大小写不同且同命中一关键词"的条目对，搜索少展示一条、与浏览不一致；绝大多数用户无此类兄弟 URL。

## P-24（BC-2 落地附带）：全文搜索不支持布尔算符（AND/OR/NOT/NEAR）是刻意设计，保留字按普通词字面匹配——请确认符合预期
- **背景**：BC-2（提交 `456970e`）修 `BuildFtsQuery` 时，大写 `AND/OR/NOT/NEAR` 此前生成 `AND*` 触发 `fts5: syntax error` 整条查询崩。修法遵循 `ItemRepository.BuildFtsQuery` 类注释既有语义"空格分隔=全部 AND、**不实现布尔算符**"：把这四个词**降级为普通检索词**（小写化去算符身份后仍走前缀），既不崩、又能按字面召回含该词的条目（如搜 `AND` 命中 "bread **and** butter"）。

## P-27（BI 后台代理线索 #6 + 横向复现）：多处 `string[..N]` 定长截断未做代理对（surrogate pair）护栏，会把一个 emoji 从中间劈成孤立高代理项
- **可机检定位（`[读码定位]`）**：全仓有 ≥5 处「按字符数定长截断、可能落在代理对中间」的写法，且**无任何一处**做 `char.IsHighSurrogate` 收尾护栏：
  - `DittoSource.FirstLine:83` `line = line[..maxLen] + "…"`（maxLen=140，产出 → `Item.Title`，入库 items.title 并随备份 JSON 序列化）；
  - `TrayHost.cs:120-121` `title[..63]` / `message[..255]`（→ 原生 `szInfoTitle`/`szInfo` toast）；
  - `DiagnosticsService.cs:131` `value[..12] + "…" + value[^6..]`（两处边界均可劈开代理对）；
  - UI 侧同形：`ItemCard.xaml.cs:86` 与 `ItemContextMenu.cs:116` 的 `Title[..40] + "…"`。
- **缺陷实质**：当被截文本恰好在第 N 个 code unit 处是一个非 BMP 字符（emoji / 部分 CJK 扩展 BMP 外汉字）的**高代理项**，`s[..N]` 会得到一个以孤立高代理项结尾的**非法 UTF-16 串**。这在纯读码层面即无争议地"错"——产出的字符串本身不合法。
- **可达性 / 影响判断（BN 已运行验 → 定级=纯外观 cosmetic）**：① 触发前提是被截那行的第 (maxLen-1) 位恰为一个 emoji 的高代理项——Ditto 剪贴板首行、toast 标题等含 emoji 且正好卡在边界，属低频。② **下游后果已于 BN 用纯 .NET 探针实跑坐死（非 `[v]`，`Microsoft.Data.Sqlite` 与 `System.Text.Json` 皆可进程内测）**：令一个以孤立高代理项 `U+D83D` 结尾的串走 `SqliteCommand.AddWithValue`→`SELECT` 回读——**不抛异常、行长不变、唯尾字符被静默替换为 `U+FFFD`（替换符）**；再走 `JsonSerializer.Serialize/Deserialize`（默认编码器）——**同样不抛、不保留原代理项、也不写成 `\ud83d` 转义**，即静默替换。备份用的 `UnsafeRelaxedJsonEscaping` 与默认编码器同经 UTF-8 转码，对未配对代理项的既有设计语义即为替换非抛。**结论：既不会崩绑定/备份，也不会丢整行/污染同步，只在该标题渲染处显一个替换符 `?`——纯外观**。故此前设想的"升级为数据面缺陷"分支**已被证据排除**，本项价值回到 §TrayHost 的 "low/cosmetic" 原判。
- **为何本会话不擅自改**：① 硬约束"无运行证据不动工作码"——在未确证影响面（崩 vs 显形）前，为一个可能是纯外观的点去重构多文件截断逻辑属投机扩写；② 正确修法**不是逐点补 `IsHighSurrogate`**（易漏、五处重复），而是收口到**一个代理对安全的截断 helper**（如 `TextTruncate.Safe(string,int,appendEllipsis)`，Core/Abstractions，配"截断后必无孤立代理项"的机检契约测——与 §AP/AH 对 `Highlighter.Split` 的"切片必无损"护栏同法）再逐点替换，其中两处在 UI（`[v]`）需真机回归；③ 这是**横向架构决策**（要不要建此 helper、放哪层、覆盖哪些点），不宜在自主缺陷修里擅自铺开。
- **选项**：(A) 建代理对安全截断 helper + 契约测 + 替换全部 ≥5 处（含 UI 两点 `[v]`），一次收口；(B) 仅在可机检层三点（DittoSource/DiagnosticsService/TrayHost）就地各补一行 `IsHighSurrogate` 收尾护栏、UI 暂不动；(C) 维持现状（按"低频 + BN 已运行验=纯外观不崩"不动，与本仓对 P-20/P-26 等低频外部输入面的口径一致）。
- **我的默认处置**：本会话取 **(C)**，登记留痕。**先决条件已在 BN 满足**（探针实跑证孤立代理项被 SQLite/STJ 静默替换为 `U+FFFD`、不抛、不丢行）——原设想"若真机确认崩于绑定/备份则升级为数据面缺陷上 (A)"的**触发条件已被排除**，故 **(A) 不再是缺陷修复必需项，而降为"要不要更干净的外观"的可选打磨**（helper 只改善截断处的替换符观感，不修任何崩溃/数据完整性问题）。是否值得为纯外观点建立并铺开跨 5 处（含 2 处 UI `[v]`）的集中式 helper，属产品/审美取向，本会话不动，留 (A)/(B)/(C) 三选项供裁。
- **影响面**：仅"被截文本恰在截断边界含非 BMP 字符"的条目；纯 BMP 内容（绝大多数中英日常文本）完全不受影响。

## P-28（BL 架构评审：P-26 + S7 的共同结构根因）：`IItemSource` 契约无"读取失败/部分失败"通道 → 吞异常返回空的源在同步汇总里塌成"成功但 0 条"，与"真·空历史"不可分

  - **站点①·连接/打开失败**：`DittoDatabaseReader` 构造 `catch { _connection = null; }`（`DittoDatabaseReader.cs:42-46`）→ `DittoSource.ReadAsync:47` 走 `IsOpen==false` 分支返回空。触发含"文件不存在/被 Ditto 独占锁占用/DB 头损坏"——其中"**用户正开着 Ditto、其 DB 处于占用态**"是**日常常态而非故障**（`Mode=ReadOnly;Cache=Shared` 能否并发读视 Ditto 加锁模式而定，属 `[v]`）。此站点的吞空**应保持 lenient**（不配置/暂时读不到 ≠ 同步失败），否则每次开着 Ditto 都冒红叉。
  - **站点②·打开成功但查询失败**：`ReadRecent`/`Search` 的 `catch { result.Clear(); }`（`:91-94`、`:133-136`）仅在 `_connection!=null` 之后触发，代表"库能开、我们的 SELECT 却抛"——这才更像真正的读取/损坏异常。
  - **据此收窄 (B)**：只把**站点②（post-open 查询吞空）**改抛类型化 `SourceReadException`（协调器 `catch(Exception):111` 自动记 `Success=false`），**保留站点①（打开/IsOpen=false）返回空且 Success=true**。如此既如实上报真·读取失败，又不误伤"Ditto 开着"这一常态，且仍不动 `IItemSource` 接口。书签源同理：其 `FetchAsync` 的 `if(!IsAvailable) return Empty()`（未配置）保持成功，仅 `catch`（文件在但解析抛）上抛。机检回归可造"能开但坏表结构"的库 → 断言站点②翻 `Success=false`、"文件缺失"库 → 断言仍 `Success=true`。
  - 结论：(B) 从"语义翻转一刀切"精化为"按失败站点分级的最小改"，误报风险消除；但是否要让用户看到此类 `Success=false` 仍属产品/观感取向，本会话依旧不改、留 (A)/(B′)/(C) 供裁。
- **BP 追加条件（读 Ditto 连接串坐实·`[已核实]`，进一步收窄 (B′)）**：`DittoDatabaseReader` 构造的连接串 `Data Source={dbPath};Mode=ReadOnly;Cache=Shared`（`DittoDatabaseReader.cs:39`）**不设 `PRAGMA busy_timeout`**——与本仓自身库的 `DbConnectionFactory.Open`（`DbConnectionFactory.cs:39` 显式 `busy_timeout=5000`）形成**有意的不对称**。后果：若同步恰撞 Ditto 正在写其库（DB 短暂排他锁），我方 `ExecuteReader` 会**立即抛 `SQLITE_BUSY`**（快速失败，无 5s 等待重试）。这意味着 **(B′) 若把"打开成功但站点②查询吞空"一律改抛**，会把一次" Ditto 正忙、重试即清"的**瞬时锁竞争**也翻成 `Success=false`——即 (B′) 仍留一条新的误报通道（不同于 BO 已排除的"打开失败/未配置"那条）。
  - 据此，(B′) 真正落地前**须再补两项之一**（均非可机检低风险单点，属稳健性设计）：① 给 Ditto 读连接也加 `busy_timeout`（把瞬时 BUSY 变等待重试，多能自清），或 ② 分类 `SqliteException`——`SQLITE_BUSY`/`SQLITE_LOCKED` 视作"暂不可读"保持 lenient 空，仅"表结构缺列/DB 损坏"等真错误才上抛翻 `Success=false`。二者都要真机验证 Ditto 写锁行为（`[v]`），故 P-28 的可执行性由"站点分级 (B′)"进一步收为"站点分级 **+ BUSY/真错分类**"。
  - 净结论不变：本会话**不改**；但 BP 使 (B′) 从"看起来只差一次接口内改动"精确定性为"仍需 busy 超时或错误码分类 + 真机验证"，佐证 P-28 属需产品/稳健性设计参与的事项，绝非可擅自落地的低风险单点。

## P-31（CG 批·**新可靠性透镜：并发/事务模型**；CH 批**实跑探针更正机制**·非 pillar-1 安全面）：`ItemRepository` 写事务为 deferred `BEGIN` 且首句是 SELECT→再 INSERT/UPDATE，其"读锁升级为写锁"在并发写下**最终仍抛 `SQLITE_BUSY`/`SQLITE_BUSY_SNAPSHOT` 致整批回滚**，且 `busy_timeout=5000` 对该路径**不构成有效上界**（实测由 provider 的 30s `CommandTimeout` 定夺）；叠加 `SyncCoordinator.SyncAllAsync` **无重入闸门**使并发可达
- **可机检定位（`[已核实]`·机制与站点均已读码坐实）**：
  - `DbConnectionFactory.Open`（`src/StarMark.Data/DbConnectionFactory.cs:39`）每连接设 `PRAGMA journal_mode=WAL; …; PRAGMA busy_timeout=5000;`。AY 批注释自述该 5s 超时是为治"约 30 处各自 `Open()` 的短连接 + 后台同步并发写写争用"时的偶发 `SQLITE_BUSY`。**但 CH 实跑探针显示：对本仓 deferred"先读后写"升级路径，5s `busy_timeout` 不构成有效上界**（真实等待由 provider 的 30s `CommandTimeout` 定夺，见下机制）。
  - `ItemRepository.UpsertAsync:161-174`、`RecordItemAsync:182-193` 均以 `conn.BeginTransaction()`（`:165`/`:188`，Microsoft.Data.Sqlite 无参重载＝**deferred `BEGIN`**，不预占写锁）开事务，循环体 `UpsertOne`（定义 `:792`）内**先 `SELECT` 既有 hidden/notes/pinned/tags**（`existing.ExecuteReaderAsync:811`）**再 `INSERT … / UPDATE`**（`INSERT INTO items:845`）。`AddTagAsync`（tx `:244`）与批量导入（tx `:697` 一带）同形：**deferred 事务内"先读后写"**。
  - **SQLite/Microsoft.Data.Sqlite 语义（机制根因·`[已核实·CH 实跑探针证伪 CG 初稿措辞]`）**：CH 用一次性控制台程序（两条裸 `SqliteConnection` 打同一临时 WAL 库、`PRAGMA busy_timeout=5000` 经 `PRAGMA busy_timeout;` 读回确认生效=5000）实测两态：
    - **对端写事务仍活跃（持 `RESERVED` 未提交）时**，本 deferred 事务"读→写升级"抛 **`SQLITE_BUSY`（code 5 / extended 5）**，且**等待时长精确等于 `SqliteCommand.CommandTimeout`**（CT=2s→2022ms、CT=8s→8077ms、默认→约 30s）——**即 Microsoft.Data.Sqlite 自装 busy handler 按 CommandTimeout 重试、`busy_timeout=5000` 被其覆盖、不是"立即失败"**。CG 初稿"立即返回/绕过 busy_timeout"措辞**错误，已按实跑更正**。
    - **对端在本事务"读完(取快照)→写"的窗口内 COMMIT（WAL 版本前进）时**，本事务升级抛 **`SQLITE_BUSY_SNAPSHOT`（code 5 / extended 517）**——**这是等待永远救不回的态**（读快照已永久过期），但 provider 仍会把整段 CommandTimeout 耗完（实测 CT=2→2011ms）才上抛，即"白等 30s 后照样失败"。
    - **净机制（比 CG 初稿更准也更严重）**：并发写场景下，本仓 deferred"先 SELECT 后 INSERT"的写事务**必然最终 `SQLITE_BUSY`(5) 或 `SQLITE_BUSY_SNAPSHOT`(517) 抛错→整个 `using var tx` 回滚**；而 `busy_timeout=5000` 对这条升级路径**不构成有效上界**（真实等待由 30s 默认 `CommandTimeout` 定夺，且对 517 根本无解）——故一次瞬时竞争会让调用方（含 `DataChangeHub` 通知路径）**挂起至多约 30 秒再失败**，比"偶发快失败"更伤。
  - **可达性（触发窗口）**：`SyncCoordinator.SyncAllAsync`（`src/StarMark.Core/Sync/SyncCoordinator.cs:29-134`）**无任何 `_syncing` 重入闸门**（通读全文确认：无实例标志、无 `lock`/`Interlocked`、无 `SemaphoreSlim`），每次进 `foreach` 直接 `FetchAsync`→`UpsertAsync`（`:61`）。于是 ① 用户连点"同步"/定时器与手动重叠 → 两个 `SyncAllAsync` 并发；② 或后台同步提交事务期间，用户恰好 `AddTagAsync`/`RecordItemAsync`/`SetDone` 等写本地条目——**两条独立短连接在 deferred 升级处相遇 → 后升级方经至多 CommandTimeout 的等待后抛 `SQLITE_BUSY`；若对端恰在"读完→写"窗口内提交则抛 `SQLITE_BUSY_SNAPSHOT`(517)**。
  - **后果放大**：`UpsertAsync` 整批在**一个** `tx` 内（`:165`-`:172`），任一 `UpsertOne` 抛 BUSY → 整个 `using var tx` 未 Commit 即 Dispose=**回滚该源整批 upsert**。`SyncCoordinator` 顶层 `catch (Exception):111` 把它吞成该源 `Success=false`（`Error=ex.Message`）→ 本次该源**全量没落库**，UI 显"部分失败"，下次同步才补。属**偶发丢一整轮同步**（非崩溃、非静默成功——这点比 P-28 的"谎报成功"诚实），低频但真实。
- **与既有条目的区分（防重复登记·`[已核实]` grep 确认全档无 "deferred/IMMEDIATE/upgrade/重入" 命中）**：
  - **≠ P-19**：P-19 是 `GitHubSource.FetchAsync` 里 **ETag 检查点写序**（崩溃窗口），单源单连接、非锁升级。
  - **≠ BP 的 `busy_timeout` 注**：BP 讲的是**读外部 Ditto 库**的连接串 `Mode=ReadOnly;Cache=Shared` **未设** `busy_timeout`；本条讲的是**本仓自有库的写事务**虽设 `busy_timeout=5000`，但 CH 实测该值对本路径**被 provider 的 30s `CommandTimeout` 覆盖、且对 517 无解**。二者连接对象、读写方向不同，恰成镜像。

- **为何本会话不擅自改（逐条过四闸门，多数不过）**：
  - 闸门②（低风险单点）**不过**：修法核心是把 4 处（`UpsertAsync`/`RecordItemAsync`/`AddTagAsync`/批量导入）的 `BeginTransaction()` 改等效 `BEGIN IMMEDIATE`（或"事务首句强制一条写"以提前占 `RESERVED`）。**CH 探针反证了此修法的正确性**：立即取写锁可根除 `SQLITE_BUSY_SNAPSHOT`(517) 那一**等待永不可解**的类（不再持过期读快照），并让真·瞬时竞争退化为"进锁期 `SQLITE_BUSY`(5)、可被等待/重试消化"。但它动的是**全应用最热写路径**的事务模型，blast radius 跨多个仓储方法，且须回归"30 连接并发写"整体吞吐——非单点。
