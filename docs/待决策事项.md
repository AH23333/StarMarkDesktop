## P-1（AC-1 安全审计遗留）：`file://` 远程主机 / UNC 的进一步收敛
- **背景**：AC-1 已在 `LauncherEx.OpenAsync` 前置协议白名单闸门（`LaunchGuard.IsAllowedScheme`，仅放行 http/https/file），挡住了 `javascript:` / `data:` / `ms-msdt:` / 自定义协议等借 Shell 协议处理器执行的污染记录。但 `file` scheme 本身仍放行任意主机：`file://attacker/share/payload` 形态的 URI 会走 `StorageFile/Folder.GetFromPathAsync`，若路径不可达则退化到 `Launcher.LaunchUriAsync` → 可能触发对远程主机的 SMB 访问，存在 NTLM 哈希泄漏面。
- **为何未在本批次落地**：`file://` 有两斜杠（Everything 侧 `file://C:/...`，主机位被历史歧义处理）与三斜杠（标准 `file:///C:/...`）两种形态，用 `Uri.Host`/`LocalPath` 区分「本地盘符」与「真实远程主机」在 .NET 上有已知歧义（见 R-P1-8 与 `LocalFileIdentity.TryPathFromUri` 往返契约）。错误收敛会打挂正常本地文件打开，须真机回归全部 file 条目来源。
- **选项**：(A) 判定 `Uri.Host` 非空且非 localhost/空 → 视为远程直接拒；(B) 仅放行 `LocalPath` 能还原成有效本地盘符/UNC 白名单的；(C) 维持现状（scheme 白名单已挡住高危 RCE 面，UNC 泄漏面留待真机批次）。
- **我的默认处置**：本自主会话取 (C)，不改动可正常工作的本地打开路径；把 (A)/(B) 留给你在有真机回归时定夺。
- **影响面**：仅安全加固深度，不影响现有功能。

## P-4（AE 评审附带发现）：`UriNormalizer.Normalize` 不归一 query 参数顺序
- **背景**：AE 批自审 `StarMark.Abstractions.UriNormalizer` 时发现：`StripTrackingParams` 按**原顺序**保留参数，未排序。故同一资源的 `?a=1&b=2` 与 `?b=2&a=1` 归一后仍是两个不同串 → 两个 `source_id` → 标签/笔记被**分裂到两条记录**。这与该文件自述目的（「同一资源的不同 URL 变体归一为同一 source_id，避免重复条目把标签/笔记分裂」）直接冲突；现有 `UriNormalizerTests`（幂等/默认端口/IPv6）也未对参数顺序作断言，即当前无测试锁定"保序"这一行为。
- **为何未在本批次落地**：修法是 query 参数按 key 排序重建——但这是**去重语义变更**，blast radius 不小：① 已入库行的旧 `source_id` 不会自动改，排序只对"新写入/再同步"生效，可能让老键与新键并存反而短暂裂成两条（需配一次全库 source_id 重算迁移才干净）；② 极少数站点确实 query 参数顺序敏感（签名/回调），排序会错误合并。属"改去重口径"的产品级决策，非纯可机检缺陷，不擅改。
- **选项**：(A) query 参数按 key（+值）稳定排序 + 配一次重算 source_id 的迁移；(B) 维持现状（承认顺序变体会裂，多数书签参数顺序稳定，代价低）；(C) 仅对已知可重排的参数集排序，白名单外保持原序。
- **我的默认处置**：本会话取 (B) 维持现状、不改可正常工作的去重键；把 (A)/(C) 连同"是否要做全库 source_id 重算迁移"交你定夺。若选 (A)，我会先补一条 `Normalize_SortsQueryParamOrder` 回归再动实现。
- **影响面**：书签/来源去重粒度；若落地需伴随迁移，风险中等故未擅动。

## P-5（AJ 后台代理附带发现）：同步只增改不删——上游已移除的条目永久残留
- **背景**：`IItemSource.FetchAsync` 契约明确是「拉取**全量**条目」（IItemSource.cs:22），`SyncCoordinator.SyncAllAsync` 对每个源仅 `UpsertAsync`（存在则更新、不存在则插入），**从不删除**本次全量结果里缺席的旧行。后果：
  - GitHub 取消 Star、浏览器书签被删、Ditto 记录被过期清理/手动删——这些条目在上游已消失，但 StarMark 的 `items` 表里**永远留着**，且在「全部/搜索」里仍可被搜到、可打开（甚至可能指向已失效资源）。
  - 已核实：全仓无任何 `DELETE FROM items` 的同步对账路径（`DataChangeHub.Prune` 只是弱引用订阅者清理，无关条目）。`sync_state` 记 `last_synced_at`/`schema_version`，但无「本源上次全量键集」快照，故当前也无从判断哪些行是"这次没再出现"。
- **为何未在本批次落地**：这是**产品语义决策**而非纯可机检缺陷——"同步是否应对账删除"取决于你想要的是「只增归档（保留历史，宁滥勿缺）」还是「严格镜像上游（源删即删）」。两种都合理，删错会丢用户可能仍想留的条目/其标签笔记，blast radius 中等，不擅改。
- **选项**：(A) 严格镜像：每源同步时按 `(source, source_id)` 对账，本次全量未出现的行删除（需先给 `sync_state` 存"上次键集快照"或在删除前比对 `last_synced_at < 本次开始` 的旧行；对**非全量/分页截断**的源如 Ditto `MaxSync=500` 要防误删头部之外的旧记录）；(B) 软删/标记失效：不删行，打 `stale` 位在 UI 灰显，用户可一键清理；(C) 维持现状（只增归档），仅在设置页给「清理失联条目」手动按钮。
- **我的默认处置**：本会话取 (C) 维持现状（当前行为对用户无破坏，最多多显示）；把对账删除口径交你定。**关键坑位提醒**：若选 (A)，必须区分「源确实返回全量」与「源被 `MaxResults`/`MaxSync` 截断」——截断源做全量对账会把未出现在首页的合法历史条目误删。Ditto(`MaxSync=500`)、Everything(分页)、以及任何 `FetchAsync` 内部带 LIMIT 的源都不满足"全量"前提，除非其 `FetchAsync` 改为无上限游标遍历。

## P-6（AK GitHub 复核）：「最近 Star」排序实为按仓库 push 时间，非用户 star 时间
- **背景（`[读码定位]`）：** 批次 Y 落地的搜索结果排序里 `sort=starred`（"最近 Star"）在 `ItemRepository.cs:71` 取 `json_extract(extra_json,'$.StarredAt') DESC`；而 `GitHubSource.MapToItem:93` 把 `StarredAt = ParseUnixTime(repo.PushedAt)` —— 即**仓库最后一次 git push 的时间**，不是"用户点 Star 的时间"。两者语义差异大：一个老仓库被新近 Star 会排到很后面；一个热门仓库每天 push 会一直霸榜。
- **根因不是编码笔误，而是一个**事实上过时/错误的近似假设**：** `GitHubClient.cs:52,86-87` 注释称「starred_at 不可用，需要从 pushed_at 替代」，并把 `Accept` 设成 `application/vnd.github+json`。GitHub 文档明确：`/user/starred` 只要把 `Accept` 换成 `application/vnd.github.star+json`，响应即变为 `[{"starred_at":"...","repo":{...}}]` 信封，**starred_at 是可用的**，并非"不可用"。故这是"可实现但当年选了近似"的欠账，不是无解限制。
- **可行性（为何本自主会话未落地）：** 修法=首页 `Accept` 改 `…star+json` + 反序列化改为信封模型（`List<StarEnvelope>{ string StarredAt; GitHubStarApiModel Repo }`）+ `MapToItem` 用真 `starred_at` 填 `StarredAt`（`updatedAt` 仍可用 repo.UpdatedAt）。改动纯逻辑层面小，但**触碰 HTTP 请求头与响应结构**——本沙箱无 GitHub Token/网络，无法验证真实响应形态（W0/standing：GitHub 集成不可沙箱验、无运行证据不动可用网络码）。副作用可控：换 media type 会使 GitHub 返回不同 ETag，改后首轮同步条件请求自然落空→全量重拉一次，无害。
- **选项**：(A) 按上面修法取真 starred_at（最正确，需一次带 Token 的真机验证）；(B) 维持现状但把 UI 文案/tooltip 从"最近 Star"改"仓库最近活动"以消除误导（零网络风险）；(C) 维持现状不改（承认近似）。
- **我的默认处置**：本会话取现状不动网络代码；若你认可 (A)，我会在能真机回归 GitHub 时一并实施并补 `MapToItem` starred_at 单测（信封解析可机检，网络拉取仍需 `[v]`）。**若只是想尽快止损误导，(B) 是纯文案、我可立即落。**

## P-7（AM 后台代理附带发现 F2）：本地条目「删除→撤销」丢失 item_tags（及潜在 pinned）

## P-8（AN 后台代理附带发现①）：语言筛选「下拉值 vs SQL vs 内存兜底」三处口径不一致
- **背景（`[已核实]`）：** 语言筛选存在三套互不一致的比较口径。① `SearchService.SearchAsync`(`:92-96`) 的内存兜底用 `GetLanguage(item)`(`:146`)，后者对 `item.Type != GitHubStar` **直接返回 null** → 一旦设了 `filter.Language`，所有 `file/bookmark/todo/note` 行被内存丢弃（无论 SQL 是否已命中）。② 但两处 SQL(`ItemRepository.cs:95` 搜索、`:441` 浏览) 的语言过滤是**跨全部类型**的 `json_extract($.Language)=@lang`。③ 下拉数据源 `GetStarLanguagesAsync`(`:405-429`) 只枚举 `type='githubstar'`，且返回 `LanguageCatalog.Normalize(trim(raw))` 归一值，而 SQL 拿它去和**未归一、大小写敏感**的 `json_extract($.Language)` 原样相等比较。
- **判定（为何主结论非缺陷、次结论转决策）：** 代理"内存兜底静默删掉所有非 star 命中"的**头条结论实为按设计**——`LanguageDetector` 类注释(`:8-9`) 明写"语言下拉的语义是『按条目的编程语言筛选 star』"，`GetStarLanguagesAsync` 也只列 star 语言。故"选 Rust 只回 star"符合既定产品语义，非 bug。**真正待决的是次级不对称**：(a) 若将来希望语言筛选**跨类型**（书签直链 `.rs`、Everything 命中的源码文件），则 `GetLanguage` 的类型门禁是拦路缺陷；(b) 即便维持 star-only，**下拉归一值 vs SQL 原样大小写敏感比较**是隐患——`EnsureLanguage`(`:52`) 对"已带 PascalCase `Language` 键"的 extra_json **原样返回、不归一**，故若 GitHub API/种子曾回传非规范大小写语言名（如 `"c++"`），下拉给出归一的 `"C++"`，SQL `"c++"="C++"`（BINARY 排序）落空 → 该选项点开 0 结果。此触发需"库里存了非规范大小写的 Language"，本沙箱无该样本、无运行证据。
- **选项**：(A) 维持 star-only，但把 SQL 侧语言比较也改为**归一 + 大小写无关 + trim**（`trim(... ) COLLATE NOCASE = trim(@lang) COLLATE NOCASE`），与下拉和内存兜底(`OrdinalIgnoreCase`)三处对齐；纯可机检、低风险，但要动两处 SQL。(B) 让语言筛选跨类型生效（`GetLanguage` 去类型门禁、改读任意类型 `$.Language`），并让 `GetStarLanguagesAsync` 覆盖非 star——**属产品语义扩张**，需你确认是否要"文件/书签也按语言筛"。(C) 维持现状。
- **我的默认处置**：本会话不改（头条为按设计、次条触发未证实），倾向若你认可则取 (A) 做口径对齐（最小且可机检），(B) 需明确产品意愿再做。
- **影响面**：主界面语言下拉 + 文件夹树语言过滤的实际命中。

## P-10（AQ 后台代理附带发现②）：`WidgetStorage.Normalize` 在 **Load 读路径**做 `Take(200/100)` 限量 → 读取即毁数据

## P-13（AT 安全深挖附带发现）：`StarLog` 未剥离消息内 CR/LF → 日志伪造（log forging）
- **可机检定位**：`StarLog.Write`（`src/StarMark.Abstractions/StarLog.cs:28-41`）把 `message` **原样**拼进 `[{时间}] {LEVEL} {message}{NewLine}` 后 `File.AppendAllText`，全程不对消息内的 `\r`/`\n` 作剥离或转义。任何**受外部影响的串**（备份文件名、被篡改备份里的字段、来源标题、`Error(msg, ex)` 里异常 ToString 携带的用户数据）一旦含换行，即可在日志里另起一行、伪造出**没有 `[时间戳] LEVEL` 前缀的任意后续行**，破坏「一行一事件」不变式；下游日志解析/审计/grep 会被喂入伪造条目或漏检真条目。

- **选项**：(A) 先加 `LogDirectoryOverride`（复刻 `BackupService.SnapshotDirectoryOverride` 现有模式）→ 再在 `Write` 里对 CR/LF 转义 → 补上述临时目录回归测；(B) 仅做 CR/LF 转义、暂不引测试钩子（改动更小但无测锁）；(C) 维持现状。

- **AX 补充（先前未记的关键权衡：栈可读性）**：上面 (A)/(B) 的 `message.Replace("\r",…).Replace("\n",…)` 会**一并压平 `Error(msg, ex)` 的堆栈**——因 `StarLog.cs:28` 先把 `{message} {ex}` 合成一个 `message` 再交给 `Write`，`ex.ToString()` 里的合法换行（stack trace）会被转义成单行，损害崩溃排查可读性。因此"统一转义"不是零代价：它把每条日志强制变单行（对 grep/解析更友好，但人读栈变差）。三个更细的落点：
  - **(A1) 只净化 `Write` 顶层拼接、不动栈**：给 `Error(msg, ex)` 单开一条路径——`msg` 转义 CR/LF，`ex` 保持原样多行，但把栈的每个续行加固定前缀（如 `\n    ↳ `）使其不以 `[时间]` 开头，从而**既防伪记录又不牺牲栈**。可机检测：注入含 `\n[2099-01-01] ERROR 伪造` 的 msg → 物理行数仍为 1；含 `\n` 的 ex → 续行不带 `[ISO] LEVEL` 前缀。

  - **(A0) 仅净化 msg、ex 原样**（P-13 原 (A)）：最小改动，但栈里的外部数据（如含换行的被污染 title 经 `ex.Message` 流入）仍可伪造——防得不全。
  - 结论修正：**推荐 (A1)** 取代原默认 (A)——它是唯一"闭合伪造 + 保留栈可读 + 防外溢到 ex.Message"三全且可机检的方案，代价是 `Error(msg, ex)` 需与 `Info/Warn` 分流。测试钩子仍按 (A) 加 `LogDirectoryOverride`。本会话仍不改（跨切面门面 + 有 devex 权衡 → 守"不擅改"纪律）。
- **✅ CD 批（2026-09-21）已按 (A1) 落地（commit `02a8edd`）**：承上"推荐 (A1)"，CD 实际实现——`Write(level, message, ex?)` 分流：`Info/Warn/Error(msg)` 走 `SanitizeMessage`（消息主体 CR/LF 折成字面量、无换行逐字节透传）；`Error(msg, ex)` 令 `ex` **不再折进 message**，改由 `StackTail(ex)` 输出——堆栈保留多行、每续行前缀四空格缩进（等价于文档设想的 `↳` 前缀，取更朴素的空格），使任何续行都不以 `[` 起始 → 伪造头 `\n[2099…] INFO evil` 即便在 `ex.Message` 里也只作缩进文本、不被 `^[时间戳]` 锚定误认新条目。**两处安全目标兼得、无栈压平代价**。

## P-27（BI 后台代理线索 #6 + 横向复现）：多处 `string[..N]` 定长截断未做代理对（surrogate pair）护栏，会把一个 emoji 从中间劈成孤立高代理项
- **可机检定位（`[读码定位]`）**：全仓有 ≥5 处「按字符数定长截断、可能落在代理对中间」的写法，且**无任何一处**做 `char.IsHighSurrogate` 收尾护栏：

- **缺陷实质**：当被截文本恰好在第 N 个 code unit 处是一个非 BMP 字符（emoji / 部分 CJK 扩展 BMP 外汉字）的**高代理项**，`s[..N]` 会得到一个以孤立高代理项结尾的**非法 UTF-16 串**。这在纯读码层面即无争议地"错"——产出的字符串本身不合法。
- **可达性 / 影响判断（BN 已运行验 → 定级=纯外观 cosmetic）**：① 触发前提是被截那行的第 (maxLen-1) 位恰为一个 emoji 的高代理项——Ditto 剪贴板首行、toast 标题等含 emoji 且正好卡在边界，属低频。② **下游后果已于 BN 用纯 .NET 探针实跑坐死（非 `[v]`，`Microsoft.Data.Sqlite` 与 `System.Text.Json` 皆可进程内测）**：令一个以孤立高代理项 `U+D83D` 结尾的串走 `SqliteCommand.AddWithValue`→`SELECT` 回读——**不抛异常、行长不变、唯尾字符被静默替换为 `U+FFFD`（替换符）**；再走 `JsonSerializer.Serialize/Deserialize`（默认编码器）——**同样不抛、不保留原代理项、也不写成 `\ud83d` 转义**，即静默替换。备份用的 `UnsafeRelaxedJsonEscaping` 与默认编码器同经 UTF-8 转码，对未配对代理项的既有设计语义即为替换非抛。**结论：既不会崩绑定/备份，也不会丢整行/污染同步，只在该标题渲染处显一个替换符 `?`——纯外观**。故此前设想的"升级为数据面缺陷"分支**已被证据排除**，本项价值回到 §TrayHost 的 "low/cosmetic" 原判。
- **为何本会话不擅自改**：① 硬约束"无运行证据不动工作码"——在未确证影响面（崩 vs 显形）前，为一个可能是纯外观的点去重构多文件截断逻辑属投机扩写；② 正确修法**不是逐点补 `IsHighSurrogate`**（易漏、五处重复），而是收口到**一个代理对安全的截断 helper**（如 `TextTruncate.Safe(string,int,appendEllipsis)`，Core/Abstractions，配"截断后必无孤立代理项"的机检契约测——与 §AP/AH 对 `Highlighter.Split` 的"切片必无损"护栏同法）再逐点替换，其中两处在 UI（`[v]`）需真机回归；③ 这是**横向架构决策**（要不要建此 helper、放哪层、覆盖哪些点），不宜在自主缺陷修里擅自铺开。
- **选项**：(A) 建代理对安全截断 helper + 契约测 + 替换全部 ≥5 处（含 UI 两点 `[v]`），一次收口；(B) 仅在可机检层三点（DittoSource/DiagnosticsService/TrayHost）就地各补一行 `IsHighSurrogate` 收尾护栏、UI 暂不动；(C) 维持现状（按"低频 + BN 已运行验=纯外观不崩"不动，与本仓对 P-20/P-26 等低频外部输入面的口径一致）。

## P-33（EN 后值正确性透镜·Explore 子代理发现，本会话读码坐实）：关键词搜索的 `LIMIT/OFFSET` 施加在**过滤与用户排序之前**，导致带筛选/非默认排序时结果被静默截断且排序错序

## P-42（B4 分页 · 本会话读码定案）：本地文件「加载更多」不能简单用 `Offset += 100`——合并页会静默丢条目
- **背景（`[读码定位]`）**：B2/B3 已落地，`EverythingInterop.Query` 的 `sort/offset` 形参与 `SearchFilter.Offset` 通道**已接通**（`SetOffset` 导出实测存在于自带的 `Everything64.dll`），只差 UI 的「加载更多」按钮。之所以停在半步：`SearchService.SearchAsync` 是**先把 FTS 页与实时源页合并、去重，再 `Take(filter.MaxResults)` 截断**（`SearchService.cs:86-129`）。若 UI 直接令 `Offset = Results.Count` 推进，两条腿各自 `LIMIT 100 OFFSET 100`，而第 1 页只展示了合并后前 100 条（被 DB 行占掉的名额，Everything 侧那几十条**从未展示过**）→ 第 2 页把它们永久跳过，用户看到"翻一页少一批文件"。这不是措辞问题，是分页游标语义问题。
- **可选路线**：(A) **每源各自游标**：`SearchFilter` 带 per-source offset（或让 `SearchService` 返回 `NextCursors`），加载更多按源推进——正确，但要动编排契约 + `IItemSource` 签名（UI/Core/Data 三处），中等工程量；(B) **单源分页**：仅当来源 chip=「本地文件」且无标签时走 Everything 一条腿（跳 FTS 腿），此时 `Offset` 语义精确——但会**丢掉库内文件行的标签/笔记富化**（虚拟行 Id=0 无标签），与"统一用标签/笔记管理本地文件"的既有产品承诺冲突；(C) **不做分页，改为提高单次上限 + 收窄引导**（如文件来源 `MaxResults=300`，空/满页文案引导用「类型筛选」或更长关键词）——零风险，但"翻完一整盘"的能力仍缺。
- **本会话实证（写至一半已回退，未留半成品）**：真按 `Offset = Results.Count` 推进写过一版 UI 翻页，推演即坐实上述丢失——第 1 页合并顺序是「FTS 在前、实时源在后」再 `Take(100)`，库内文件行会先占满名额、Everything 同区间的行被截掉；下一页两腿各前进 100，那段没展示过的 Everything 行就**永久不可达**（用户表现为"翻一页少一批文件"）。故代码回退，只留本条决策。
- **(D) 候选正解（本会话读码得出，推荐优于 (A)）**：把 `SearchFilter.Offset` 的语义从"每腿各偏移"改成"**合并后切片**"——两腿一律取 `LIMIT (offset + size)`、不再各自 OFFSET，由 `SearchService` 在合并去重之后 `Skip(offset).Take(size)`。改动只落在 `SearchService` + `ItemRepository` 的 limit 绑定，无需 per-source cursor、不动 `IItemSource` 签名，且不丢条目；代价是深页时两腿各多取 offset 条（Everything 是内存索引，`SetMax` 上限 20000 内可接受），并且可与已接好的 `Everything_SetOffset` 形参并存（后者留给 (A) 用）。
- **我的倾向**：(D) 是改动面最小的正解，(A) 次之，且需要一次真机验收（分页结果是否重复/漏项）；(B) 表面最省但会侵蚀已有承诺，不建议；(C) 可作为临时缓解。四闸门②③不过（涉及编排契约面 + 须真机 `[v]`），故登记不擅自做。
- **影响面**：只影响「本地文件」结果超过一页（100 条）时的浏览深度；Star/书签分页维持现状（同样有该缺陷，但此前无人翻页，未暴露）。
- **✅ 已定案并落地（`a654ef5`，路线 D 的编排侧变体）**：偏移不在任何一条腿内施加，而是由 `SearchService` 用 `SearchFilter.WithFetchWindow(offset+size)` 把**两条腿的窗口统一加宽**、一律从 0 取，合并去重+分段后再 `Skip(offset).Take(size)`。比原 (D) 描述更进一步：加宽放在编排处而非各腿，否则漏改某个 `IItemSource` 就会"深页静默少一批"（实测正是先写成各腿各自 +Offset，联合测试跑出 110≠160 才改过来）。SQL 侧 `OFFSET @offset` 与 SDK 侧 `Everything_SetOffset` 一并撤掉。UI 加「加载更多」（`HasMore` 驱动），按 `PreviewDedupeKey` 去重后追加。测试 `Paging_*` 5 例钉住不重不漏。
- **残留（新登记 P-49）**：FTS 的 `LIMIT` 在 CTE 内、早于外层 type/lang/hidden/标签谓词 ⇒ 重过滤时页偏短、`HasMore` 可能提前为 false（不跳条目，但"翻不到底"）。另：纯浏览态（空关键词）与「按标签浏览」分支走 `GetAllAsync`，`BrowseFilter` 无偏移 ⇒ 不分页，入口按 `CanLoadMore=false` 收起。

## P-49（分页正确性·GN 轮新登记）：FTS 腿的 `LIMIT` 在 CTE 内、早于外层谓词 ⇒ 重过滤时"翻不到底"
- **`[读码定位]`**：`ItemRepository.SearchAsync` 的 SQL 形状是 `WITH fts_hits AS (… ORDER BY rank LIMIT @limit) SELECT … WHERE type/lang/hidden/标签谓词` —— 先按相关度截断，**之后**才套用外层过滤。GN 把 `@limit` 语义定为"取到本页末"（`MaxResults + Offset`，由 `SearchFilter.WithFetchWindow` 加宽），于是：若 top-N 里有一大半被外层谓词滤掉（选中语言、只看某类型、含隐藏关闭、多标签 AND），`ordered` 会短于 `offset + size` ⇒ 页偏短，且 `HasMore = ordered.Count > offset + page.Count` 会**提前判 false**，用户看到"只有 60 条"而实际还有更低相关度的命中没露过面。

- **可选解**：(A) 把外层谓词下进 CTE（`items_fts JOIN items` 后统一 WHERE，再 LIMIT）——最正确，但要重写这条 SQL 并逐条复核标签 AND 语义与 `bm25` 排序；(B) 按选择率放大 `@limit`（如 `2*(offset+size)`）——廉价但只是缓解；(C) 现状 + 页短到时给"结果可能被筛选收窄，试着放宽筛选"的提示——零风险，用户可自助。
- **我的倾向**：先 (C)（一句文案），(A) 留给"搜索质量"专轮并配真机验收。闸门②③不过（触及查询主干 SQL + 须度量），故登记不擅改。

## P-61（已定案·不做静态加密）：条目明文存在本地 SQLite，不接 DPAPI
`[评估后定案]` 考虑过 `CryptProtectData`（当前用户域）加密 `description`，判为**净负收益**：
1. **废掉搜索**：`search_text` 索引的是 `CjkTokenizer.ExpandForIndex(正文)` 的明文 token，正文明文消失 ⇒ 剪贴板历史只剩"按标题翻"，与 Ditto/Win+V 的核心价值脱节。
2. **废掉备份与迁移**：DPAPI 当前用户域密文在**换机器 / 重装 / 换账户**后不可解 ⇒ `backups\`（含 P-51 的每日自动备份）里的剪贴板件变成永久砖，这是"看起来有备份、真需要时全是乱码"的最坏形状。
3. **本机威胁模型里收益接近零**：能读该 DB 文件的进程，通常已能以同一用户身份调 `CryptUnprotectData`。加密挡住的是"拷走文件的人"，挡不住"跑在你会话里的人"。
4. 现状护栏已是**三层拦截 + 两条用户控制**：默认关闭（`ClipboardHistoryEnabled` 可空 bool，未点就不采）、密码管理器前台整条不记、PEM/JWT/卡号形状不记、正文上限 32 KB、随时「暂停记录」、随时「清空历史」（确认框带真实条数）。口径与 Ditto 的明文本地库保持一致。

### P-77（产品取舍·计算器）：「时间戳」换算整页摘除后，要不要在别处留一条开发者向通道 —— **批次 MT 内已决：不留**
**形状**：批次 LA 给计算器加了「时间戳」页（Unix 秒/毫秒/微秒 ⇄ 日期，含"用此刻"与"复制秒值"）。发起人 2026-09-24 判定"不知所云、很少有该计算需求"，该页已整页换成「常用」速算（打折满减 / 涨跌回本 / 单价比较 / 间隔天数），`TimestampConverter` 与其 22 条用例一并删除。仍可能想要它的是"从日志里抓一段 1727000000 看是几点"这一类开发者场景。
**决策与理由（安全 > 稳定 > 性能，且不影响正常使用）**：**不保留、不搬家**。① 这不是"数据没了"，功能与判据在 git 历史里完整可查（`git log --follow -- src/StarMark.Core/Calc/TimestampConverter.cs`，含逐条位数判精度与范围闸门测试），恢复成本是一次 cherry-pick 级别的工作，不是一次考古；② 把它塞进今日速览/搜索结果/任何一个别的页面，都是"用一次的人极少、看见的人全被占一行"的典型形状——本产品已按"臃肿防线"摘掉过语言筛选、钉查询、标签云三处同类东西；③ 计算器已有三页，再加一页会让"哪页放什么"重新变模糊。
**触发重开的条件**：真机验收时发起人点名要时间戳（或出现"日志里的秒值想快速看日期"这类具体场景）⇒ 作为「常用」页里的第 5 种速算加回来（槽表新增一项即可，不需要新页签），而**不是**恢复旧页或新建组件。
**已核到哪一层**：`[读码]`——删除是彻底的（全仓无 `Stamp/Clock/UnixStamp` 残留引用，build 与全量测试在删除后 0 警告 0 错误 / 1487 全绿）。**没有核实**的是"有多少真实用户会想要它"，这条本就属产品判断。

### P-78（产品取舍·计算器）：「常用」页上次选的速算模式要不要记住 —— **批次 MT 内已决：不记**
**形状**：速算模式下拉（打折满减 / 涨跌回本 / 哪个划算 / 间隔天数）每次打开组件都回到第一项。要记住它，就是给 `WidgetInstanceConfig` 加一条按实例持久化的字段，并牵动快照的采集 ⇄ 还原对称（`WidgetSnapshotSymmetryGateTests` 会要求它进快照，否则"应用快照回到那一刻"却停在别的模式上）。
**决策与理由**：**视图态不进持久化**，与"当前停在哪个页签""换算页选了哪两个单位"同一口径（后者本轮也从不保存）。一次速算通常几秒完成，把"上次算的是涨跌"存下来的收益，小于多一条字段 + 多一处快照字段 + 多一条老用户迁移规则的代价。
**触发重开的条件**：真机反馈出现"我每次都只用最上面那一个，能不能让它停在那儿"⇒ 记。届时按 P-66/IX 那批的既有做法处理：`int?` 语义（null＝从没配过 ⇒ 默认第一项，0＝用户主动选到第一项 ⇒ 保持），并同步进快照的采集与还原两侧。
**已核到哪一层**：`[读码]`——`WidgetInstanceConfig` 现无该字段，快照对称守门当前两侧都不含速算模式（守门测试按字段名比对，不会因缺少它而误报）。
### P-79（产品取舍·贴图）：贴图要不要支持不透明度 / 旋转 / 标注（Snipaste 都有） —— **批次 MV 内已决：v1 都不做**
**形状**：可行性分析 §2.7 把 Snipaste 贴图窗的能力列为"透明度、旋转、标注编辑器"三项，D3 只裁定了"贴图窗不进出组件体系且有数量上限提示"，没逐项定这几条。本批落地了缩放 / 拖动 / 穿透 / 复制 / 存图 / 关闭，没落地这三项。
**决策与理由（安全 > 稳定 > 性能，且不影响正常使用）**：
- **不透明度**：技术上要 `SetLayeredWindowAttributes`，而 WinUI 3 的窗是 DWM 重定向呈现的，这个调用在**组合窗上不保证生效**——最坏的形状不是"没效果"而是"整块画不出内容变成黑框"。本仓库的规矩是：没有实测证据就不往能跑的路径上叠原生调用（批次 MJ 那次 PDH 方案被本机实测推翻就是前车之鉴）。要做得先在真机上验一遍，验通再接。
- **旋转**：贴图的主要用途是"把一块画面留在那儿对照"，旋转的使用面比截图标注窄得多，而它要改的是渲染层（`RotateTransform` + 命中测试与拖动的坐标换算 + 缩放中心），会污染刚钉死的那套几何判据。
- **标注编辑器**：那是一个独立的功能量级（画笔/矩形/箭头/文字/撤销/另存），且已登记为截图 L2/L3 的路线，不该混进"能贴住"这一格。
**触发重开的条件**：真机验收时用户点名要其中一项。**最可能的第一个是不透明度**（贴在大段文档上看字透不下去），届时的做法是：先在本机验证 `SetLayeredWindowAttributes` 在贴图窗上确实生效且不退化，再从右键菜单加"半透明"一档（与穿透同属"全体/单张"口径要先定）。
**已核到哪一层**：`[读码]`——三项都**未做任何实测**；当前贴图窗的 ex-style 只动了 TRANSPARENT/LAYERED/TOOLWINDOW 三位。

### P-80（产品取舍·贴图）：贴图要不要跨会话保留（重启后还在原位）
**形状**：现在贴图窗是纯运行期对象：`PinManager` 只持有一张进程内名册，重启后全消失，位置/缩放/穿透都不落盘（也不进快照、不进布局方案）。要保留就是"每张贴图 = 一份 PNG 落盘 + 一条元数据（位置/缩放/穿透）+ 启动时重建"。
**决策与理由（按 D3 的"贴图窗不进出组件体系"推）**：**不保留**。贴图的价值在"此刻对照一下"，而它的成本是常驻内存（上限 12 张、每张一份像素）；把它做成能跨重启恢复，语义上就变成了组件（用户会开始期待它也参与布局、快照、"显示所有组件"），那正是 D3 明确要避开的合并。**要留东西就用组件或待办**，这两条通道已经存在且带持久化。
**触发重开的条件**：真机反馈出现"我重启电脑是为了腾内存，但希望那几张图还在"这类明确诉求 ⇒ 按"导出为图片 + 手工再贴"的轻量方案做（不引入贴图元数据格式），而不是把它升级成第 17 种组件。
**已核到哪一层**：`[读码]`——`widgets.json` 与快照模型都不含任何贴图字段（本批刻意没加，`WidgetSnapshotSymmetryGateTests` 也因此不受影响）。
### P-81（产品取舍·识字）：OCR 结果要不要另外留一份（"识别记录"页 / 自动进剪贴板历史 / 自动存成随记） —— **批次 MX 内已决：都不留**
**形状**：识字现在的产物只有一段写进剪贴板的文字。要留档有三条现成的路：① 不登记回声，让它作为一条新内容自动进内置剪贴板历史；② 自动落一条随记/条目；③ 做一个"识别记录"页。
**决策与理由（安全 > 稳定 > 性能）**：**都不留，且刻意登记回声让它不进历史**。
- **安全是这里的决定性理由**：识字的典型手滑是框到密码框、验证码、令牌、身份证号——OCR 恰恰最擅长认这些清晰印刷体。让它自动进"明文存储、且不接 DPAPI"的剪贴板历史（P-61 已定案：明文存储、不接 DPAPI）等于给这类内容开了一条静默归档通道。登记回声（`App.NoteClipboardOwnWrite`）后，这段文字只存在于用户主动粘贴的去处。
- ②③ 属"为新功能再造一个存储面"：一段临时提取的文字，价值在两分钟内被粘走，而不是长期占一个列表；要留用户自己粘进随记/待办（那两处有既定的敏感拦截与删除路径）。
- 结果就是**剪贴板历史页不会因为识字而多出条目**，也就不会出现"我明明只按了一次识字，历史里怎么多了一大段"。
**触发重开的条件**：真机反馈出现"我要连续认好几块文字，粘一次丢一次" ⇒ 做①的受控版本：识别结果先攒在一个可见的浮层里（用户挑一条复制），仍然不落库；只有用户明确"存"才进随记。若用户要求"识别过的都要能找回"，那属新产品定位（OCR 归档），需要先重开 P-61 关于明文存储的口径——**那时安全优先级会盖过便利性，不能直接做**。
**已核到哪一层**：`[读码]`——`OcrService.TryCopyText` 已登记回声；识别链路不写任何库表与设置项。**没有实测**的是"用户在真实密码管理器界面上识字会发生什么"（属真机面）。

### P-82（产品取舍·识字）：要不要给用户一个"识别语言"选择器
**形状**：现在引擎固定取用户配置语言（本机 `zh-Hans-CN`）。系统里另有 en-GB / en-US / ja 可用；截一段日文或英文资料时，用中文引擎认会明显更容易出错（实测中文引擎认英文代码是准的，但日文假名混排时中文引擎会拆错）。
**决策与理由（稳定 > 性能，且不影响正常使用）**：**v1 不做选择器**。① 用户配置语言对绝大多数场景是对的（本机就是中文）；② 加一个语言下拉就要解释"为什么这里还有一个语言"，而系统给的语言列表在各机器上不同（有人只有 en-US）——这会让"认不出字"的原因更模糊而不是更清楚；③ 提示里已经把**实际用的语言**写出来了（"按 zh-Hans-CN 识别"），用户与我们都看得见，是判断要不要重开的最直接证据。
**触发重开的条件**：真机出现"认外文错得没法用"的具体样本 ⇒ 加"用哪种语言认"的选择（候选取自 `AvailableRecognizerLanguages`，默认仍是用户配置语言，并按截图/识字分别记住），同时把"这块画面里没有认出文字"的文案改成带当前语言的版本。
**已核到哪一层**：`[本机实测]`——`AvailableRecognizerLanguages` 与 `RecognizerLanguage` 都取到过真实值（见进度报告 §八十二）。**未实测**的是切到别的语言后识别质量的差别。

### P-83（产品取舍·标注）：已画好的形状要不要支持拖拽改形 / 单独删除 / 选中编辑 —— **已决：不做，撤销只弹最后一条**

批次 NB 的模型是"画完即定形"（点、颜色、粗细在创建时给死），所以撤销＝弹掉列表末尾，
不需要任何反向运算，也不会出现"撤销一条却残留半条"。
要支持改形就得再加一套命中测试 + 选择态 + 手柄绘制，而截图标注的实际用法是"画错了撤销重画"，
不是"画好了挪一挪"。Snipaste 支持改形，但它的编辑层是一整个 retained-mode 场景，我们的是像素合成。

**重开条件**：用户真机反馈里出现"画歪了想挪一下而不是重画"这类具体诉求。

### P-84（产品取舍·标注）：拖动中的那一条要不要也显示成真像素 —— **已决：不做近似以外的方案**

现在松手即换成真像素，拖动中用简单图元（矩形/椭圆/折线/笔刷圆）近似。
要拖动中也是真像素，就得每帧重烤一次整块选区（最大 1920×1200，克隆 + 逐条重画），
鼠标一动就是几十毫秒一帧——拖动会明显发涩，比"末端差几个像素"难受得多。

**重开条件**：实测发现近似与真像素的差异让用户误判了标注位置（目前只有粗细边缘差 1–2px）。

### P-85（产品取舍·标注）：形状边缘要不要抗锯齿 —— **已决：先不做，等真机眼睛裁决**

文字走 GDI 所以是 ClearType（观感好），形状是自己描的圆点序列所以是硬边。
补抗锯齿要引入覆盖率计算（Wu 线、椭圆解析覆盖度），代码量与出错面都不小，
而 2–8px 的标注线在屏幕上硬边几乎看不出来。**这一条属于"只有眼睛能判断"的那类**，
所以明确标注出来：如果用户看了觉得毛刺明显，再单独做，而不是现在凭想象加。

### P-86（产品取舍·标注）：打码要不要提供"高斯模糊"外观（现在是方块马赛克）

马赛克格子边长 12 物理像素，效果是"知道这里有字但读不出"——这正是遮敏感信息要的。
高斯模糊在低倍率下**仍可被还原**，作为隐私手段反而更弱。所以默认只给马赛克。
如果将来要"美观优先于保密"的场景（比如做教程配图），再作为可选外观加入。

### P-87（产品取舍·网址来源）：要不要抓条目正文、要不要后台定时刷新 —— **已决：都不做**

两项都会把这一栏从"信息来源"推向"订阅阅读器"，而后者是用户明确否掉的（D4）。
具体代价：抓正文＝每条候选多一次外发请求（20 条就是 20 次，且都是第三方站点）；
定时刷新＝未经用户同意就对他的地址长期发流量。两者都不是性能问题而是**授权问题**，
所以即使将来性能有余量也不该自动开启。
（批次 RB 把这一栏搬去主窗「RSS」页之后，两条结论照旧：抓取仍然只由那一页的「刷新」那一下发起。）
**重开条件**：用户主动要求"把某条的正文收进来"时，作为「收藏」按钮的一个可选附加动作实现
（点一下抓一次，仍然由用户发起）。

### P-88（产品取舍·网址来源）：收藏之后要不要给「移除收藏」按钮 —— **已决：这一栏不做**

收藏后的条目就是一条普通本机书签，主窗/组件的条目右键本来就能删（含撤销），
在这一栏再放一个删除入口等于把同一个动作摆两处，还得各自处理"删完了这行显示什么"。
**刻意不显示「已收藏」以外的第二状态**：如果将来出现"从 RSS 收藏的东西要成批撤回"的真实需求，
再做按前缀 `rss-bookmark:` 批量列出的入口（前缀已经是可查的），而不是在这里加按钮。
（批次 RB 之后"这一栏"指主窗「RSS」页：那一页只有「收藏到文件夹」与「已收藏」两态，仍不给移除；
"已经收过"的判定改走 `GetCollectedRssLinksAsync` 那条无行数窗口的前缀查询，正是这里说的那条前缀。）

### P-89（安全口径·AI 通道）：API Key 明文落在 settings.json —— **已决：与 GitHub PAT 同一口径，登记不擅动**

批次 A 的 `AiApiKey` 与既有的 GitHub PAT（P-30）、剪贴板历史正文（P-61 已定案）形状完全相同：
都是 `%LOCALAPPDATA%\StarMark\settings.json` 里的明文，都在 CurrentUser 目录（其他用户读不到）。
**刻意不给 AI Key 单独接 DPAPI**：只加密这一格会造成"Key 有保护、PAT 没有"的不一致，
而真正的修法是把两处一起包一层 DPAPI（含存量明文回落 + 透明升级），那属凭据处理口径，需用户拍板。
**重开条件**：P-30 放行时把 `AiApiKey` 一并纳入同一层封装，勿单独动一处。

### P-90（产品取舍·AI 整理）：应用之后要不要"整批撤销这次整理" —— **已决：暂不做，等真机感受**

现在能撤的路径是：条目右键 → 标签编辑器里删掉那个标签（逐个），活动流里每条都有一笔「修改」。
批量回滚要的是另一套东西：给每次应用打批次号 + 一张"这次加了哪些标签"的关联表，
且必须区分"这个标签是 AI 加的"与"用户自己早就加过同一个"——否则撤销会连用户的手工作一起删。
**这一条属于"只有真机用过了才知道疼不疼"的那类**，先按现路径交付。
**重开条件**：用户反馈"应用完觉得不对，一条条删太累"。

### P-91（口径·AI 整理）：一次上限 500 条够不够、要不要"全库整理" —— **已决：够，且不做全库一把梭**

候选只挑"没有标签的条目"，所以**反复点「开始整理」就会自然推进**：上一批打完标签就不再是候选。
全库一把梭要的是断点续跑 + 进度 UI + 失败重问，代价是几百次模型调用在一次点击里发生，
中途出问题（换模型、超时、答复质量崩了）用户连看都看不见。
500 这个数按"本地小模型 50 条一批、十批上下、耗时以分钟计"定，界面上也写着最大值。

### P-92（性能口径·网络侧）：RSS 抓取与 AI 批量整理要不要改成有界并行 —— **已决：暂不做**

两处都是"逐源/逐批串行"，并行确实能把最坏等待时间压到 1/N。但本轮的原则是
**只改能被回归守住的量**：网络往返的收益只有秒表能看见，而秒表在这类环境里测不出结论
（代理、丢包、服务端限流都在动），改完既没法证明快了、也无法防止将来退回串行或改出并发 bug。
现状已给了出口：RSS 一轮 60 秒自动收手 + 「停止抓取」立即生效，AI 整理按批落检查点可暂停续跑。
**重开条件**：出现"实测等待时间过长"的真机反馈；那时也应当先加计数（每轮耗时、批次数）再加并行。

**【RF-3 更新 · RSS 那半边已翻案，AI 那半边仍不做】**用户真机点名的正是"实测等待时间过长"
（"每次刷新极为缓慢"），所以重开条件已满足。落地的不是"并行"这一件，而是四条一起：
落盘缓存（含 ETag 跨进程复用）、**抓取并发上限 4**、打开页面只补抓到期的源、增量并入。
并发这里仍然守住了本轮原来的顾虑：**判据不是秒表**——`SourcesAreFetchedConcurrentlyButBounded`
钉的是"同时在飞的源数落在 2…4 之间"与"结果顺序＝配置顺序"这两个整数，
把并发改回串行必红，所以它是一条能回归的性质而不是一次运气。
**AI 批量整理那半边维持暂不做**：它的瓶颈是模型生成时间，并行会同时放大 token 消耗与失败面，
且已有"按批落检查点 + 可暂停"的出口。

### P-93（体验·拖放回执）：一次拖入若全部重复，快捷启动不给任何回应 —— **已决：登记待做，排在性能批次之后**

现象：往「快捷启动」拖一批文件，如果这些入口已经存在（或者路径为空），松手后界面<b>什么都没发生</b>——
没有"已添加 N 个"，也没有"这 M 个已经在里面了"。PA-6 之前 `QuickLaunch_Drop` 里那个 `added` 计数
算完从来没被读过，等于代码自己知道、用户不知道。

为什么不顺手修：要让它"看得见"，得先给组件窗口加一个<b>短暂回执</b>的出口（一行状态文本 + 自动收手）。
`WidgetWindow` 现在没有任何这类基础设施（全仓扫过：无 `DispatcherQueueTimer`/状态条），
新造一条 UI 通道不是性能批次的活，塞进来只会两边都做不实。

落地口径（重开时照这条做，别重新设计）：回执长在<b>用户刚操作的那个组件窗内</b>（不弹主窗、不弹通知），
添加成功给"已添加 N 个"，全被去重给"N 个都已经在快捷启动里"，一条都不给的情况（实例找不到／写盘失败）
必须说原因；同一实例的回执复用同一个文本槽，后一次覆盖前一次；不用秒表判断"够不够短"。
**重开条件**：性能批次收尾后作为界面小项单独做；或真机验收时用户点名"拖了不知道有没有成"。

### P-94（性能·快照）：跨实例合并成一个连接/一个事务 —— **已决：暂不做**

PA-9 已经把"为空的实例逐台开库确认"省成一次问话（12 实例 2 台有内容 ⇒ ~24 次连接降到 3 次）。
剩下的部分是：捕获与还原对**有内容的那几台**仍各开一次连接。合并成一次连接/一个事务能再省两三次，
代价是把现在"单实例失败可继续（其余照常还原）"换成<b>全有全无</b>，而快照保真链
（`GetLocalItemsForInstanceAsync` / `ReplaceLocalItemsForInstanceAsync`，字段对称由
`WidgetSnapshotSymmetryGateTests` 守着）是全仓库最 delicate 的一段，V1a/V1b/V1c 三批才立起来。
按"安全 > 稳定 > 性能"，这点收益不抵风险。
**重开条件**：真机说"应用快照明显慢"（那时先测一次应用要几毫秒，再决定合并到哪一层）。

### P-95（截图标注·工具条）：纯图标到底认不认得出来 —— **待真机裁决**

RC-2 按"用图标不要文字"把整条工具条改成 15 颗图标（8 工具 + 笔 + 撤销/重做/清空 + 复制/存图/贴图/识字/取消），
文字全部挪进 ToolTip 与顶部提示行。**图标形状是代码画的矢量**（不用图标字体，缺字会变方块），
但"这两颗点分不分得开画笔和荧光笔""再点当前工具换颜色这条用法找不找得到"这两件事**只有眼睛能判断**，
而我这边无法操作截图遮罩（一按 Esc 就没了），所以不凭想象宣称已经好用了。
**如果真机看不懂**，按代价从小到大三条现成退路：① 把 ToolTip 换成图标下的常驻小标签（条子会长一点）；
② 只把最常错的"画笔/荧光/打码"三颗换成更夸张的形状差（例如荧光笔加一条底色横带）；
③ 恢复"颜色/粗细"两颗下拉但缩成图标尺寸。
**重开条件**：真机验收时点名"看不出哪个是什么"或"找不到换颜色"。
**同族新增一项（批次 RB）**：导航栏「RSS」那颗图标（E8A1，一张带文字行的卡片）。
它不是猜的——候选码位在 *Segoe Fluent Icons* 与 *Segoe MDL2 Assets* 里各渲染一张对照图后选的，
两套字体都有这个码位且形状一致（缺字会变方块，那类问题只有眼睛能发现）。
若真机觉得"不像订阅"，退路是换 E7BC（几行左对齐的列表线）或 E909（地球），同样先渲染再定。

### P-96（RSS·浏览器侧）：把订阅收藏同步进浏览器书签 —— **已决：这一版先不做**

用户裁决原话："这一版先不做浏览器侧"。技术上另有一道硬门槛：Chromium 系浏览器的
`Bookmarks` 文件带 `checksum`（MD5 校验，改了内容不重算就会被静默丢弃并回退到 `Bookmarks.bak`），
本仓库今天对该文件**只读不写**；手改一个带校验和的用户数据文件属于"改坏了用户东西没法自愈"那类风险。
**重开条件**：用户明确要求，且届时要先解决"改坏必须能还原"——写前备份 + 校验和重算 + 失败回滚，
并确认浏览器处于关闭态（开着会覆盖）。不做只读侧的半套同步。

### P-97（截图标注·批次 RE-3）：文字的旋转不做 + 「为什么不直接抄现成编辑器」 —— **旋转一项已被 RF-2 翻案（现在做，且有像素级判据）；"对象层自写、零依赖"的结论不变**

用户真机反馈"无法移动编写文字的位置/缩放/方向"。移动与缩放已落地（四角＝缩放，框内＝移动），
**方向（旋转）这一项对文字刻意不给**，理由分两层：

1. **技术上**：`GdiTextDrawer` 那条路是"把字写进一块与文字框同样大小的 32 位临时画布，再逐行搬回目标缓冲"。
   要旋转就得换成世界变换矩阵（`SetWorldTransform` + `ModifyWorldTransform`）并自己重算旋转后的
   包围盒与裁切——风险全在像素层，而这一层在本仓库里恰恰是**断言不到的那一部分**
   （今天能断言的只有 BGRA 缓冲上的位序、混合次数、可重复性）。
   与之相对，几何类标注（矩形/椭圆/直线/箭头/折线/画笔/荧光/打码）的点集是模型里的数，
   旋转后的点位可以逐点断言，所以那几类给了旋转把手。
2. **产品上**：**把手不给，比给了不生效诚实**。文字的顶部那颗圆点根本不会画出来
   （`Annotation.SupportsRotation => Tool != Text`），而 `Problem()` 会明确说"文字不支持旋转
   （只能移动与改字号）"——用户不会点了半天才发现这条路是假的。

**退路（若真机点名要旋转文字）**：① 把整条标注（含文字位图）画进一块离屏 BGRA，再对它做
双线性旋转——代价是一次全图重采样，字会有轻微糊边；② 换 `Direct2D`/`WriteableBitmap` 的变换层
来渲染预览，但这会把"预览由 Core 在像素上画"这一条单一口径拆成两套；③ 只做 90° 离散步进
（0/90/180/270），这四个角度下包围盒仍是整数轴对齐，可断言，实现量最小。**推荐 ③**。
**重开条件**：真机验收时明确"要给文字转方向"。

**【RF-2 更新 · 重开条件已满足，文字旋转已落地】**用户第二次仍报"且无法旋转"，所以这一项做了。
走的是退路 ① 的**缩小版**：不是全图重采样，而是"字模先画进临时位图 → 按**覆盖率图 + 双线性**合成回画布"
（`GdiTextDrawer.DrawRotated`，`ANTIALIASED_QUALITY`，碰过的像素 alpha 一律补 255）。
原来那段顾虑里说"像素层断言不到"被证伪了一半——**旋转后的形状仍然可断言**：
`RotatedTextBoundsCoverEveryPixelItPaints` 在 0/30/90/180/270 五个角度上比对"真画出来的像素集合"
与"`Bounds()` 那个框"，框罩不住任何一个墨点就红；`TextBoundsGrowWithRotation` 钉住中心不歪。
另一处要更正：**`Annotation.SupportsRotation` 这个旗标已删**（所有工具都能转，留着就是假口径），
所以本条上面那句"`SupportsRotation => Tool != Text`、顶部圆点根本不画"在今天的代码里已经不成立，
读到时请按"文字与几何类同样给旋转把手"理解。

#### 同批附带记录：为什么没有"直接用现成项目"

本轮收到明确指示"能使用现成的项目就直接使用，抄源码或者进行封装都可以"。逐条查过（结论：都不比自写便宜）：

| 候选 | 授权 | 不选的具体理由 |
| --- | --- | --- |
| ShareX（截图 + 标注编辑器） | **GPL-3.0** | 传染性授权，抄源码或静态链接都会把整个 StarMark 拖进 GPL 义务；封装要走进程外，等于把截图/贴图/识字四条链的落点全部改造成 IPC |
| ScreenToGif（帧编辑器） | MS-PL（宽松） | 编辑器画在 **WPF**（本仓库是 WinUI 3， visual 树不通用）、相关类型大量 `internal`、且它的形状/文字与"帧"数据模型耦合；**它自己也没有"事后选中一段文字再改"** —— 用户要的那件事它没做 |
| WinUI 3 自带 InkCanvas / InkToolbar | — | **WindowsAppSDK 2.3.6 的 WinUI 里没有这两个控件**（UWP 才有），也没有 WPF 的 `AdornerLayer` 可做选择框装饰层 |
| Fabric.js / Konva（JS 画布） | MIT | 要走 WebView2 ⇒ 同一张图两套渲染栈，且 BGRA 缓冲要在原生像素与 JS 之间来回搬（每帧整张拷一次），截图遮罩这种"按下即全屏"的场景延迟不可控 |
| tui-image-editor | MIT | 项目已归档停止维护，且同样是浏览器侧 |

所以取的是**最小对象层**：`Annotation` 加三个变换量（`Pivot`/`Rotation`/`Scale`）＋
`TransformedPoints()`/`Bounds()`/`Corners()`/`Contains()` ＋ `AnnotationPainter.HitTest`，
UI 侧加"点住即拖"的抓取链。**零新增 NuGet 依赖**，且预览与交付仍共用同一个 `Render`（那条
"架构先问输出能不能被实测"的口径没有破）。

### P-98（截图标注·批次 RE-3）：「点住已选中的那条就拖」与「在它里面再画一个框」的冲突 —— **本轮取 Snipaste 语义，手感待真机裁决**

批次 RE-3 让"画完的那一条自动选中"，而**选中状态下按在它包围盒里就变成拖动**（框内＝移动、四角＝缩放、顶圆点＝旋转）。
这条语义有一半概率不合用户的手：他想"在刚画的大框里再圈一个小框"时，第一按会被吃掉成移动。
本轮选 Snipaste 那套的三个理由：① 用户反复用 Snipaste 作对照，学到另一套反而要重新适应；
② "点一下空处取消选中，再拖就是新框"只多一步，且**点空处那一按本身现在有反馈**（批次 RE-3 把"点了没反应"改成选中脚下那条）；
③ 显式「选择」模式要给一行 9 颗的工具条再加一颗，而那一行的紧凑度是批次 RC-2 用闸门钉住的（真机反馈原话"布局膨胀"）。

**如果真机说"我想在里面再画一个却把旧的拖走了"**，两条退路按代价排序：
① 只在**把手与描边附近**（±12 物理像素）才允许拖动，框内让给新的一笔——改动最小，代价是"移动"要点在边上，需要一句提示；
② 加一颗显式「调整」模式按钮（模式与工具分开，不进 `AnnotationTool` 枚举，避免每处 switch 与图标闸门都要跟着改），
进入后点选/拖动都归它，退出＝点任意工具。
**重开条件**：真机验收时点名"再画一个框结果把旧的拖走了"，或"拖动太难点中"。

### P-99（RSS·批次 RF-3）：一天一次 / 并发四路 / 每源留 60 条 —— 三个数字是我定的，已按下述口径生效，等真机裁决

用户给的是方向（"每天仅刷新一次，且增量刷新"），具体取值由我定，理由与代价都写在这里，方便一次改到位：

- **24 小时**：与"每天"字面一致，也是订阅阅读的日常节奏。代价是"他早上看完、晚上有了新文章，
  第二天早上才出现"。**如果真机觉得太久**，改一处即可：`RssFeedCache.AutoRefreshGap`（例：12h 或 6h）。
  界面那句话不会留在旧数字上——"隔多久抓一次"只由 `RssFeedCache.GapText` 产生（24 小时说"一天"、
  6 小时说"6 小时"），页 VM 里那四处引用它，XAML 里连"一天/每天"这类词都不许出现（闸门
  `TheCadenceIsStatedInExactlyOnePlace` 钉着）。会一起变红的是**故意钉在 24h 边界上**的那两条 Theory
  （"差一秒不到一天不打扰 / 正好一天到期"），那是提醒把边界值一起改掉，不是回归。**不建议**做成设置项：多一格数字要多解释一句话，
  而"要不要现在就看新的"已经有「刷新」按钮在回答。
- **并发上限 4**：四个一并跑，坏源只挡住自己那一路；不是"来多少开多少"——订阅地址是第三方站点，
  几十路并发等于对人家做一次小范围压测，本机连接池也会被占满。真要调，改 `RssAggregator.MaxParallel`。
- **每源留 60 条**（`KeepPerSource`）：与解析上限 `RssSourceConfig.MaxEntries` 同数，
  缓存这一层就不会再截一次（两处各一个数＝必然出现"其中一个改了另一个没改"）。界面上另有 30 条一屏 +
  「展开更多」，那是渲染口径，与存储无关。

**重开条件**：真机验收说"看不到新的"（把 24h 调小）或"打开时等得还是久"（把并发调大 / 把 60 调小）。

### P-100（RSS·批次 RF-3）：要不要给「清空缓存」一个就地入口 —— **已决：不做，留一句话说明什么情况下要回来做**

现在这一页只有两个动作：「刷新」（无视到期判断，现在就去问一遍）与逐条「收藏」。
没有"把本机这份 `rss-cache.json` 清掉"的按钮。三个理由：

1. 它没有对应的用户意图。**"我要看新的"由「刷新」回答**（条件请求，源说没变化就一个来回），
   "我要重下一遍"这种诉求在订阅阅读里几乎不存在。
2. 空间不是问题：每源最多 60 条纯文本，几十个源也就几十 KB 量级，为它开一个"删除"入口
   反而多一条误操作路径（清掉之后进页面就是一片空，还得再抓一次）。
3. 缓存坏掉的情况**已经不需要人工干预**：读不出来就按空档继续（日志分开记路径/权限/损坏三种原因），
   写不进去会直接在那一句状态里说"缓存没能写进磁盘（下次进这一页还得重抓）"。

**重开条件**：真机出现"这一页显示了一份我不想显示的内容，且刷新也带不走它"——
那时要做的也不是"清空"，而是让「刷新」在那一源上强制忽略缓存重问一次（把两个动作分开命名）。

## 本轮实测证伪（别再当缺陷找）
- **GitHub 时间戳不会被机器历法带偏**：`2024-05-01T12:00:00Z` 在 th-TH/ar-SA/my-MM/zh-CN 下都得同一瞬间（.NET 的 ISO 快路）。锁 `InvariantCulture` 只是防"日期退化成 `2024-05-01`"那类形状（GS 已按纵深防御落地）。
- `Everything64.dll` 只按 `AppContext.BaseDirectory` 与自有 `sdk\` 两处绝对路径 `NativeLibrary.TryLoad` ⇒ 不会捡到系统里另一份不同版本的 DLL；`Everything_Startup` 前用 `TryGetExport` 探测，1.4/1.5 都不会 `EntryPointNotFoundException`。
- `WidgetStorage` 降级态：`.tmp`+`Move`、失败删 tmp、下次成功 `Load` 自动清位 ⇒ 无永久降级、无泄漏；`SettingsStore` 的 `.bad` 保留同理。
- 文件夹树不枚举磁盘（全部由库内条目构路径）⇒ 不存在 `System Volume Information`/他人目录的 `UnauthorizedAccessException` 面。
- OneDrive 占位文件：`PreviewHost` 的 `File.OpenRead` IOException 已被兜住并出文案，不崩。
- `DataChangeHub`：弱引用 + 锁内快照 + 单处理器异常隔离；`DbConnectionFactory` 用 builder 转义 `;`/`=`。
- `WidgetAppearanceEditor` 的 `ToUpper()` 只作用于 `#RRGGBB`（无 i），土耳其语安全；`EverythingInterop.ParseCsvLine` 的无文化解析在生产链路无调用者（仅测试引用）。
