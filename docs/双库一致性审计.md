## 0. 一句话结论

两库**今天没有任何数据通路**（备份格式双向硬拒，见 §1），所以"一致性"的实际含义不是"能不能同步"，
而是**"同一个概念在两边是不是同一个定义、同一个用户动作会不会得到不同结果"**。
按这个口径查出 **6 条需要回灌或至少写清的分歧**，其中一条是**扩展侧已按用户实测踩坑修过、桌面侧原样还在**（§7，本批最有价值的一条）。

## 1. 备份 / 导入导出：双向硬拒，且"故意不同"没有任何地方声明 [亲验]

| 项 | 桌面 | 扩展 |
|---|---|---|
| `app` 字面量 | `"starmark-desktop"`（`StarMark.Core/Backup/BackupEnvelope.cs:13`） | `'starmark'`（`src/core/backup.ts:45`） |
| 读取时的闸门 | `app` 不等即拒：`BackupService.cs:176` "这不是 StarMark 桌面版备份（app=…）"；**无校验和也拒**：`:183` | `backup.ts:93` `if (parsed.app !== 'starmark' \|\| !Array.isArray(parsed.items))` 抛错 |
| 校验和 | 有：SHA-256 over 规范化 payload（`BackupService.cs:517-522`） | [代理] 全仓 grep `checksum` 无命中；替代物是可选 AES-GCM 信封（`backup.ts:56-62`） |
| `version` | 写 1，只挡"比我新"（`BackupService.cs:178-180`） | 写 2（`backup.ts:45`），**读时不校验 version** |
| `items` 位置 | 在 `payload` 内（`BackupEnvelope.cs:43-61`） | 在顶层（`backup.ts:5-10`） |

**判定：现状安全**（两侧都进不去对方的文件，不会"半兼容地读坏用户数据"）。
**但有三处值得写清**：
1. 这个互斥是靠**两个字符串碰巧不同**实现的，不是靠一条声明——将来有人"顺手统一 app 名"就会打开一条没有兼容代码的通道；
2. **`version` 号位各走各的**：扩展的 `2` 与桌面的 `1` 不是同一条时间线，谁看谁的版本号都会误判（桌面读扩展件会以为"比我新，请升级"）；
3. 桌面导出**条目不带标签**（`BackupRepository.cs:34-38` 的 SELECT 无 `tag_names`；`BackupService.cs:261` 注释自认），
   标签走 `payload.tags/itemTags` 另一份——扩展若将来只读 `items` 就会静默丢标签。
⇒ 登记 **P-117**。

## 2. AI 分类的批次边界：80 的理由引用了一个不存在的实测 [亲验]

- 桌面：`MaxItemsPerBatch = 80`（`Abstractions/Ai/AiClassify.cs:107`），注释原文——
  > "批次边界重新交还给'模型抄录可靠度'来定（再大漏抄率上升，**扩展侧实测过的拐点之前**）"（`AiClassify.cs:104-106`）
- 扩展：`CLASSIFY_BATCH_SIZE = 50`（`src/core/ai/classify.ts:50`）。

**两处对不上**：① 扩展用的是 **50**，80 在它**后面**，不是"拐点之前"；② 两库里都**找不到**所谓"实测过的拐点"——
扩展侧唯一的实测痕迹就是它自己选了 50（而那句 50 在桌面注释里被定性成"长摘要时代为了压预算定的"，那是桌面的历史，不是扩展的实测结论）。
⇒ 这是 R1 查出的 `WithoutAlreadyTagged` 同族：**注释把一个自己没做过的测量当成了外部依据**。登记 **P-116**。

其余参数对照 [代理]（值本身可信，用途见 §9 的抽查说明）：

| 参数 | 桌面 | 扩展 |
|---|---|---|
| 标题截断 | 40 字，超限加 `…`（`AiClassify.cs:121,169-172`） | 不截（`classify.ts:115` 原样发） |
| 摘要 | 仅标题薄于 12 字时顶 40 字兜底（`:122-123,156-162`） | 无条件发前 80 字（`classify.ts:115`） |
| 每条标签上限 | 3（`AiClassify.cs:64`，注释称"对齐扩展侧实测"） | 3（`classify.ts:52`）**这条对齐成立** |
| 标签长度 | 24 硬截（`AiClassify.cs:33,57`） | 代码不校验，提示词写"不超过 6 个字" |
| 参考标签数 | 40（`AiClassify.cs:111`） | 8（`classify.ts:86 seedCategories(max = 8)`） |
| 用户段预算 | 18 000 字，与条数双判 | 无预算闸 |
| max_tokens | `clamp(n*28, 400, 4000)` | OpenAI 4000 / Anthropic 200 / Ollama 不设 num_predict（`num_ctx: 8192`） |
| 温度 | 0.2 | 0.2 ✔ |
| 请求超时 | 180 s/批 | **无超时**（只有 20 s 保活心跳），见 §8 |
| 单批失败 | 记 `Ok=false` 继续下一批 | 整轮中止并写 error，靠 `state.batch` 断点续跑 |

答复解读的形状差异 [代理]：桌面认四种（含 `编号: 标签一、标签二` 行格式为第一公民），扩展认三种且**没有行格式**、
裸数组仍要求元素带 `i`/`id`（不是按序对位）；`categories` 一边是对象映射、一边是 `[{tag, ids}]`——
**同名不同形状**。桌面把越界编号计入 `UnknownIds` 上报，扩展静默丢弃。

## 3. O2 规则截胡是桌面独有的 [亲验]

## 5. 数据模型与标签 [代理，含一处本批复核]

- 标签存储：桌面是关系表 `tags` + `item_tags`（`Schema.sql:76-91`），**读侧仍用 char(31) 拼一列再拆**——
  `GROUP_CONCAT(t.name, char(31))`（`ItemRepository.Items.cs:28`，另见 Search.cs:72 / Local.cs:29,88 / Snapshots.cs:32），
  拆回 `ItemRepository.cs:91`；扩展是 Dexie 行内数组（`db.ts:383`）。
- 去重大小写：**桌面不区分**（`Schema.sql:78 COLLATE NOCASE` + `AiClassify.cs:66 OrdinalIgnoreCase`），
  **扩展区分**（`db.ts:397` `if (v && !out.includes(v))`）⇒ 同一批手输标签，扩展会留下 `前端` 与 `前端 ` 式近义/大小写双份，桌面会并成一条。
- 时间戳：**桌面 Unix 秒**（`Schema.sql:3` 明文；`ItemModel.cs:92`），**扩展 epoch 毫秒**（`types.ts:44` + `Date.now()`）
  ⇒ 与 §1 的"互不导入"一致，**目前没有换算 bug**，但任何未来的通道都必须显式换算，且换算点只该有一处。
- 用户态字段：共有 `hidden` / `notes`；桌面多 `pinned`（且 `notes` 列与 `notes` 表并存）；
  扩展多 `summary/embedded/reviewedAt/reviewCount/reviewSkip`。两边都**没有软删除时间戳**。

## 7. 【最有价值的一条】GitHub 仓库 URL 归一：扩展按用户实测修过的坑，桌面还在 [亲验]

扩展 `src/core/normalize.ts:40-45` 原文：
```
// github.com 永远 https，且 www.github.com 归一为 github.com：
// 否则 http 书签与 https Star 会成为两行、同仓库被误报"疑似重复"（用户实测踩坑）
if (host === 'www.github.com') url.hostname = 'github.com'
if (url.hostname === 'github.com' || url.hostname.endsWith('.github.com')) {
  if (url.protocol === 'http:') url.protocol = 'https:'
```
桌面 `StarMark.Abstractions/UriNormalizer.cs:24-60` 全段里**没有 www 处理、没有协议改写**（只做 host 小写、默认端口清零、
path 去尾斜杠并钳回 `/`、GitHub 段收窄到 `/{owner}/{repo}`、`tab` 参数清空）。
⚠ **别把这条说过头**：子域判据桌面**是有的**——`UriNormalizer.cs:67-68`
`host == "github.com" || host.EndsWith(".github.com", OrdinalIgnoreCase)`，所以 `www.github.com` 在桌面同样走 GitHub 分支去收窄 pathname。
桌面缺的**恰好只是那两件事**：把 `www.github.com` 折叠成 `github.com`、把 github 的 `http:` 改写成 `https:`。

⇒ **同一仓库在桌面会裂成两行**（`http://github.com/o/r` 书签 + `https://github.com/o/r` Star；带 `www.` 的那份同理），
而扩展侧那句"用户实测踩坑"说明这个 bug 真实发生过并已被修掉。
登记 **P-118**，建议＝**回灌桌面**（一行 www 折叠 + 一处协议改写，两件事都在 `Normalize` 里，改动面极小），
属稳定性/数据正确性类，按"安全 > 稳定 > 性能"排前面的批次里算靠前。

其余归一化分歧（同条 P-118 内一并处理）：
- **尾斜杠的删除层级不同**：桌面只删 path 层并**保留根 `/`**（`UriNormalizer.cs:39-45`，注释专门写了幂等理由）；
  扩展删**整串尾**斜杠（`normalize.ts:53-54`）⇒ `https://ex.com` 与 `https://ex.com/` 两边标准形不同。
- **path 大小写**：扩展主键前整串 `toLowerCase()`（`normalize.ts:110`）⇒ `…/A` 与 `…/a` **同键**；
  桌面只小写 host，`source_id` 不折叠 ⇒ **裂成两条**（SQLite TEXT 默认 BINARY）。
- **跟踪参数名匹配**：桌面 `OrdinalIgnoreCase`（`UriNormalizer.cs:17-21`，注释写"11 个"实为 10 个）；
  扩展 `Set` 精确匹配（`normalize.ts:1-12,37`）⇒ `?UTM_SOURCE=x` 桌面删、扩展不删。
