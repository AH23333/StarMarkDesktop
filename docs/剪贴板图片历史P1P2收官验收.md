## ⑥ 遗留与风险（不做纸面承诺）

**只能真机量、沙盒给不出数的（不许被理解成"应该没问题"）**
1. **LOH 与采集瞬时峰值**：一帧 4K 的 BGRA 是 33 MB，PNG 编码 + 缩略图 + 身份哈希同窗存在；
   §6 原话是"连续 20 张 4K 截图复制，任务管理器口径"。代码侧只做到"全程线程池、不碰 UI 线程"。
2. **大量图目录下的占用统计与启动对账耗时**：两者都是整目录 stat/枚举，200 张与 5000 张不是一回事。
3. **Office 系连发通知的去抖实感**：700 ms 是猜的起点，决议明写"实测定值"。
4. **缩略图实际字节数**：`BitmapEncoder` 的 q60 在 C# 投影里不可达（现吃编码器默认质量），
   设置页那句"约为其 160px 的 JPEG"因此可能偏乐观。
5. **`SetBitmap` 写回后各家目标的粘贴兼容性**、以及**自家写回是否真不产生第二条历史**：
   像素身份的往返已在机检里钉死，但"系统把 PNG 重排成 CF_DIB 之后字节是否逐字相等"只能真机验。
6. **各来源截图的格式命中分布**（微信/QQ/浏览器/Office/终端/系统截图工具）：2b 之后**解码由自研一份承担**，
   这条从"格式命中"升级为"必须重验颜色是否逐通道正确"。

**明确不接的形状（给了原话，不是静默丢弃）**：隔行（Adam7）PNG、位深 1/2/4。
判据：截图链上见不到它们（这类小图系统会先展成 DIB）。若真机日志出现"图片帧解不出像素（PNG：不支持的位深（4））"
这类行，那是新证据——按 §7 走裁决，不自作主张扩接。

**既有事实、本批未动（动它就是越 P1 的边界）**：`ShowsPreview => !isRssCandidate` 让文本历史行也带
"预览"那颗按钮（点开走 PreviewHost 的文本兜底，显示正文）。它不是本功能引入的，也不改变文本行为。

**工程侧遗留**：`origin/main` 停在 `44d337e`，本地未推已达 130+ 个 commit（含本功能 7 个）——推送需用户明确指示。

## §6 真机确认清单（结转，一条都不写"应该没问题"）

1. 打开图片采集后逐来源复制图片（微信 / QQ / 浏览器 / Office / 系统截图工具 / 终端）：
   格式命中、尺寸正确，**且列表里那张小图红蓝不反、每行第二个像素起没有条纹**。
2. 点图片行"再复制" → 画图 / Word / 浏览器粘贴：图要对，且**历史不许多出一条**（回声）。
   若多出来，把 `%LOCALAPPDATA%\StarMark\logs\starmark-YYYYMMDD.log` 里"剪贴板"相关行给我——
   那一句会决定是像素不一致还是登记时序不一致，我不靠猜改。
3. 16 位 PNG 来源（某些看图软件复制出来的）：以前会被拒，现在应能记录并正确显示。
4. 连续 20 张 4K 截图复制：任务管理器看瞬时峰值与是否卡住。
5. 从资源管理器手删 clip 目录里某条的两张文件 → 重启：条目仍在、写明"文件已不在本机…可直接删掉"；
   点它给"复制不回去（条目仍保留，可置顶或删除）"。只删缩略图那张 ⇒ 不标缺失，改走主图回退解码。
6. 设置页：两个开关默认值与那条警示原文第一次就能看到；把上限从 200 改成 2000 的途中不应丢历史；
   占用统计那两行给出真实目录路径。
7. 大量图（几百张）时打开设置页的占用统计耗时、启动后对账是否影响首屏。
